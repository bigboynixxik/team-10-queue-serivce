# Backend — сервис пользовательской очереди «Авито Очередь»

Настоящий документ описывает серверную часть системы управления очередью на приобретение товара ограниченной доступности, реализованную в рамках кейса хакатона Авито.

Сервис выполняет три функции: помещает покупателя в очередь до перехода к оформлению заказа, выдаёт временное персональное право на покупку и обеспечивает освобождение неиспользованного права по истечении установленного срока.

Технологический стек: язык Go 1.26, хранилища PostgreSQL и Redis, каналы реального времени на основе WebSocket и Server-Sent Events, развёртывание средствами Docker Compose.

## 1. Применение ИИ

При разработке серверной части в качестве вспомогательного инструмента применялись модели `Claude Opus 5`, `Gemini 3.1 Pro` и `GPT-5.6-Codex`.

Область применения ограничена вспомогательными задачами:

- подготовка документирующих комментариев в формате `go doc` к экспортированным сущностям;
- написание тестов, не затрагивающих критические сценарии распределения остатка;
- рутинные правки и приведение кода к принятому стилю;
- анализ конечного автомата очереди на предмет расхождений с проектной документацией.

Архитектурные и продуктовые решения — разделение слоёв, выбор хранилищ, правила конечного автомата и модель права на покупку — приняты командой самостоятельно. Результаты работы моделей подлежали проверке и приняты только после ревью; предложения, противоречащие проектным решениям, отклонялись.

По результатам анализа выявлены два расхождения между документацией и реализацией: превышение выделенного остатка при частичном предложении и отсутствие проверки права перед оформлением заказа. Оба зафиксированы в виде задач и устранены отдельными изменениями, выполненными разработчиками.

## 3. Порядок запуска

### 3.1. Развёртывание средствами Docker Compose

Рекомендуемый способ. Выполняется из корневого каталога репозитория:

```bash
cp backend/.env.example backend/.env   # при первоначальной настройке
docker compose up -d --build
docker compose ps                      # контроль состояния служб
```

Миграции схемы применяются автоматически при инициализации сервиса. Прикладной интерфейс доступен по адресу `http://localhost:8080`; при обращении через обратный прокси-сервер фронтенда — `http://localhost/api/v1`.

| Служба | Порт | Назначение |
| --- | --- | --- |
| `backend` | 8080 | Прикладной интерфейс, WebSocket, SSE |
| `frontend` | 80 | Статические ресурсы клиента, проксирование `/api` |
| `avitomock` | 9090 | Заглушка внешней системы AvitoBackend |
| `postgres` | 5432 | Долговременное хранилище |
| `redis` | 6379 | Очереди, остатки, публикация событий |

Готовность к работе подтверждается переходом всех пяти служб в состояние `healthy`.

### 3.2. Запуск в среде разработки

Наличие PostgreSQL и Redis обязательно. Рекомендуется развернуть их средствами Docker Compose, а сервис запускать локально:

```bash
docker compose up -d postgres redis avitomock
cd backend
cp .env.example .env    # в переменных PG_DSN и REDIS_ADDR указать localhost
go run ./cmd/api
```

## 5. Архитектура

### 5.1. Организация слоёв

Применена слоистая архитектура с односторонним направлением зависимостей:

```
transport → service → repository → хранилища
                ↓
             models
```

| Слой | Зона ответственности |
| --- | --- |
| `transport` | Разбор запроса, выбор представления ответа, преобразование доменных ошибок в коды HTTP |
| `service` | Правила функционирования очереди: конечный автомат, распределение остатка, обработка истечений |
| `repository` | Взаимодействие с PostgreSQL и Redis без знания предметных правил |
| `models` | Сущности предметной области и доменные ошибки |
| `pkg` | Инфраструктурная обвязка: журналирование, корректное завершение, пулы соединений, миграции |

Интерфейсы объявляются на стороне потребителя. Интерфейс `transport.QueueService` определяет требования транспортного слоя, интерфейс `service.DurableRepo` — требования слоя бизнес-логики. Реализации о существовании этих интерфейсов не осведомлены, что обеспечивает независимую замену и тестирование слоёв.

Изоляция пакета `models` обеспечивается принудительно: правило `depguard` конфигурации статического анализа запрещает импорт пакетов `pgx` и `squirrel` в доменный слой. Сущности предметной области не должны содержать сведений о способе их хранения.

### 5.2. Обоснование выбора хранилищ

PostgreSQL и Redis решают различные задачи, взаимная замена которых невозможна.

Предотвращение состязания за последнюю единицу товара обеспечивается сценарием Lua, выполняемым в Redis: решение о выдаче принимается атомарно в рамках единственной операции. PostgreSQL в принятии решения не участвует.

Сохранность принятого решения обеспечивается PostgreSQL: запись выполняется после того, как решение принято в Redis.

Порядок операций записи фиксирован: сначала PostgreSQL, затем Redis. При аварийном завершении процесса между операциями кэш оказывается устаревшим и подлежит повторному чтению из долговременного хранилища. Обратный порядок создавал бы интервал, в течение которого Redis содержит решение, отсутствующее в долговременном хранилище.

Детальное описание приведено в документах `docs/storage/redis.md` и `docs/storage/postgres.md`.

## 7. Особенности реализации

### 7.1. Версионирование прикладного интерфейса

Клиентские конечные точки размещены под префиксом `/api/v1`, вынесенным в константу `api.APIPrefix`. Изменение, нарушающее обратную совместимость, может быть опубликовано как `/api/v2` при сохранении обслуживания существующих клиентов версией `v1`.

Конечная точка `/healthz` намеренно размещена вне версионированного пространства: она относится к инфраструктурному контролю работоспособности, и проверка состояния контейнера не должна нарушаться при смене версии интерфейса.

### 7.2. Разграничение доступа

Конечные точки разделены на три группы с различными механизмами контроля.

| Группа | Инициатор вызова | Механизм контроля |
| --- | --- | --- |
| `/api/v1/queue/*`, `/api/v1/me/queues`, `GET /api/v1/rights/{token}` | Браузер покупателя | Заголовок `X-User-Id` |
| `POST /api/v1/internal/rights/{token}/validate`, `POST /api/v1/rights/{token}/events` | Внешняя система AvitoBackend | Заголовок `X-Internal-Token` |
| `GET /api/v1/queue/{id}/stats`, `/healthz` | Произвольный | Отсутствует |

Обоснование. Полноценная аутентификация вынесена за пределы кейса требованием `FR-D1`. Защита межсервисных конечных точек при этом обязательна: в их отсутствие произвольный субъект мог бы подтвердить оформление заказа либо зафиксировать оплату чужого права. Публичность конечной точки статистики допустима, поскольку ответ содержит исключительно агрегированные счётчики без идентификаторов пользователей.

### 7.3. Право на покупку

Право идентифицируется непрозрачным значением UUID, не содержащим кодированных данных. Принадлежность устанавливается посредством поиска: по предъявленному значению извлекается запись права, после чего её поле `user_id` сравнивается с идентификатором обратившегося.

Обоснование. Отсутствие данных внутри идентификатора исключает как подделку, так и необходимость криптографической подписи.

Требования `FR-C1` и `FR-C2` реализуются двумя конечными точками, различающимися инициатором вызова и назначением.

Конечная точка `GET /api/v1/rights/{token}` предназначена клиентскому приложению: код `200` обязателен до перехода к оформлению заказа. Предъявление права, принадлежащего иному пользователю, возвращает код `403`; предъявление истёкшего либо использованного права — код `404`. Проверка отвечает за предсказуемое поведение интерфейса и снижает нагрузку, отсекая недействительные попытки на подступах.

Конечная точка `POST /api/v1/internal/rights/{token}/validate` предназначена внешней системе и составляет границу доверия. AvitoBackend вызывает её до создания заказа и обращения к платёжной подсистеме, передавая идентификатор товара; заказ создаётся исключительно при ответе `204`. Проверяется, что право действует, не израсходовано и выдано именно на указанный товар.

Обоснование разделения. Клиентское приложение исполняется в браузере и находится под управлением пользователя, вследствие чего его вызовы не могут служить гарантией: клиент способен пропустить проверку либо обратиться к оформлению заказа напрямую. Решение о допуске принимается той стороной, которая создаёт заказ, а конечная точка защищена разделяемым секретом и из браузера недоступна.

### 7.4. Ограничение числа одновременных очередей

Число очередей, в которых пользователь состоит одновременно, ограничено значением `MAX_ACTIVE_QUEUES`. Превышение отклоняется кодом `409` с телом `{"error":"queue_limit_reached","limit":5}`; отдельное тело необходимо, поскольку тот же код возвращается при исчерпании товара.

Место занимают исключительно действующие членства. Состояния `PURCHASED`, `DECLINED` и `SOLD_OUT` являются терминальными и место освобождают, вследствие чего завершённое участие не расходует ограничение бессрочно.

Перечень занятых очередей ведётся множеством Redis. Проверка предела и занятие места выполняются единым сценарием Lua: раздельное выполнение допускало бы одновременное прохождение проверки несколькими параллельными запросами. Повторный вход в очередь, где пользователь уже состоит, места не расходует, вследствие чего повторные отправки формы и переподключения ограничением не затрагиваются.

Освобождение места привязано к переходу членства в терминальное состояние, а не к отдельному вызову. Единственное исключение составляет подтверждение оплаты по уведомлению внешней системы, изменяющее состояние непосредственно в Redis; освобождение выполняется в том же сценарии Lua. Множества восстанавливаются из PostgreSQL при запуске наравне с остальным состоянием кэша.

Обоснование. Ограничение направлено против удержания единиц товара, недоступных прочим покупателям: пользователь, состоящий в предельном числе очередей, не может удерживать большее число единиц. Ограничивается участие, а не приоритет, вследствие чего порядок обслуживания FIFO сохраняется неизменным.

### 7.5. Множественность представлений ресурса

Конечная точка `GET /api/v1/queue/{product_id}/members/me` формирует ответ в одном из трёх представлений в зависимости от заголовков запроса:

- при обычном запросе — документ JSON с текущим состоянием;
- при наличии заголовка `Upgrade: websocket` — канал WebSocket;
- при наличии заголовка `Accept: text/event-stream` — поток Server-Sent Events.

Аналогичный подход применён в конечной точке `GET /api/v1/me/queues`.

Обоснование. Объект `EventSource` устанавливает соответствующий заголовок самостоятельно, вследствие чего клиенту достаточно указать адрес ресурса. Выделение отдельных путей под каждый транспорт не требуется, а единство формата ответа обеспечивается конструктивно.

Для каналов WebSocket и SSE предусмотрена передача идентификатора пользователя параметром запроса `?user_id=`. Причина: браузерные конструкторы `WebSocket` и `EventSource` не позволяют задавать заголовки, вследствие чего иной способ передачи идентификатора недоступен. Приоритет сохраняется за заголовком.

### 7.6. Позиция в очереди и прогноз ожидания

Поля `position` и `eta_seconds` включаются в ответ исключительно в состоянии `QUEUED`. Пользователь, обладающий действующим правом, в очереди не состоит, вследствие чего сообщение о его позиции было бы недостоверным.

Прогнозируемое время рассчитывается как произведение числа предшествующих участников на среднюю длительность оплаты и является оценочной величиной.

### 7.7. Представление завершённых состояний

Конечная точка `GET /api/v1/me/queues` возвращает в том числе завершённые членства в состояниях `PURCHASED`, `DECLINED` и `SOLD_OUT`.

Обоснование. Исчезновение элемента интерфейса без уведомления не позволяет пользователю установить причину произошедшего. Решение о сокрытии завершённых состояний и о моменте сокрытия принимается клиентским приложением.

### 7.8. Обработка ошибок

Доменные ошибки пакета `models` не содержат сведений о протоколе HTTP. Преобразование в коды состояния сосредоточено в единственной функции `writeError` пакета `transport/api`.

Три разновидности ошибок права — отсутствие, истечение срока и повторное использование — преобразуются в единый код `404`. Обоснование: для вызывающей стороны перечисленные случаи означают одно и то же, а их различение раскрывало бы сведения о существовании идентификатора.

### 7.9. Фоновые процессы

Конечный автомат изменяет состояние по запросу пользователя. Изменения, обусловленные течением времени, выполняются тремя фоновыми процессами:

- обработчик истечений с периодичностью `EXPIRATION_INTERVAL` анализирует таймеры Redis, возвращая просроченные права в очередь и снимая нерассмотренные предложения;
- обработчик `stock_decrement_outbox` с периодичностью `STOCK_OUTBOX_INTERVAL` доставляет в AvitoBackend подтвержденные списания остатка и повторяет неудачные попытки;
- механизм подтверждения присутствия удаляет отсутствующего пользователя только из очередей `QUEUED` по истечении `USER_PRESENCE_TIMEOUT`; выданные предложения и права действуют до собственного фиксированного срока.

### 7.10. Заглушка внешней системы

Компонент `cmd/avitomock` замещает внешнюю систему AvitoBackend: хранит физический остаток товара, принимает уведомления о списании и предоставляет страницу оформления заказа.

Обоснование. В отсутствие внешней системы пользовательский сценарий не может быть пройден полностью: операция оплаты недоступна, а состояние `PURCHASED` достижимо исключительно посредством непосредственного вызова служебной конечной точки. Оба исполняемых файла собираются единым `Dockerfile` с параметром `ARG CMD`.

Конечная точка `PUT /products/{id}/stock` контрактом внешней системы не предусмотрена и предназначена для демонстрационных целей: она позволяет установить остаток товара в единицу и продемонстрировать состязание двух покупателей.

Заглушка воспроизводит и требуемое от внешней системы поведение: она проверяет право перед созданием заказа (п. 7.3) и применяет списание остатка идемпотентно, распознавая повтор по заголовку `Idempotency-Key`.

### 7.11. Устойчивость к сбоям

Хранилища, внешняя система и сам сервис могут оказаться временно недоступны. Проектное требование состоит в том, чтобы ни один из этих случаев не приводил к расхождению между проданным и списанным количеством.

**Доставка списания остатка.** Уведомление AvitoBackend об уменьшении остатка не выполняется непосредственно в обработчике оплаты. Событие фиксируется в таблице `stock_decrement_outbox` той же транзакцией, что и перевод права в `USED`, а доставляется фоновым обработчиком с повторными попытками и нарастающей задержкой до `STOCK_OUTBOX_MAX_BACKOFF`.

Обоснование. Оплата к моменту уведомления уже проведена, вследствие чего отказ внешней системы не может служить основанием для отмены операции, но и потеря уведомления недопустима: она означала бы товар, проданный в Queue Service и остающийся на складе AvitoBackend. Запись события в одной транзакции с покупкой исключает состояние, в котором покупка зафиксирована, а уведомление не запланировано. Повторная доставка безопасна, поскольку событие снабжено уникальным идентификатором.

**Обработка отложенных переходов.** Истечение права и снятие нерассмотренного предложения берутся обработчиком в аренду на ограниченный срок, а не изымаются из расписания. Успешно обработанная задача подтверждается и удаляется, неуспешная переносится, брошенная прекратившим работу процессом возвращается в расписание по истечении аренды.

Обоснование. Изъятие задачи до её обработки создаёт интервал, прекращение работы в котором означает безвозвратную потерю таймера: право осталось бы действующим без чего-либо, способного его завершить, а удерживаемая единица выбыла бы из обращения окончательно.

**Восстановление состояния.** При запуске сервис воссоздаёт содержимое Redis из PostgreSQL: остаток и число свободных единиц, порядок очереди, членства, права и таймеры. Приём запросов начинается после завершения восстановления.

Обоснование. Redis содержит состояние, необходимое для атомарного распределения, однако источником истины является PostgreSQL. В отсутствие восстановления потеря кэша означала бы утрату очереди и повторную выдачу уже удерживаемых единиц. Записи, противоречащие конечному автомату, приводятся к согласованному состоянию с фиксацией в журнале, а не препятствуют запуску: право, на которое не ссылается ни одно действующее членство, ничего не удерживает и переводится в `EXPIRED`. Отказ хранилища при восстановлении, напротив, прерывает запуск: работа с частично заполненным кэшем означала бы выдачу единиц, считающихся удерживаемыми.

## 8. Тестирование

### 8.1. Инструментальная база

| Компонент | Средство |
| --- | --- |
| Утверждения | `testify/require`, `testify/suite` |
| Тестовые двойники | `go.uber.org/mock`, генерация в `internal/service/mocks` |
| Интеграционное окружение | `testcontainers-go`: PostgreSQL и Redis |
| Тестирование HTTP | `net/http/httptest` |

```bash
go test ./...                      # полный набор; требуется работающий Docker
go test ./internal/service/...     # бизнес-логика без внешних зависимостей
go test -race ./...                # с детектором состязаний
go test -cover ./...               # с оценкой покрытия
```

Повторная генерация тестовых двойников после изменения интерфейсов:

```bash
go run go.uber.org/mock/mockgen@v0.6.0 \
  -source internal/service/interfaces.go \
  -destination internal/service/mocks/mock_interfaces.go -package mocks
```

### 8.2. Область покрытия

Приоритет отдан бизнес-логике и контрактам взаимодействия с хранилищами.

| Пакет | Предмет тестирования |
| --- | --- |
| `internal/service` | Переходы конечного автомата, поведение при отказе зависимостей |
| `internal/repository/postgres` | Корректность SQL-выражений и транзакций на действующей СУБД |
| `internal/repository/redis` | Сценарии Lua, дисциплина FIFO, резервирование при частичном предложении |
| `internal/transport/api` | Каналы реального времени: доставка изменений, завершение сеанса |
| `internal/config` | Разбор окружения и значения по умолчанию |
| `internal/models` | Валидация состояний |

Пакеты `cmd`, `pkg` и промежуточные обработчики тестами не покрыты ввиду отсутствия в них нетривиальной логики.

### 8.3. Принятые соглашения

1. Тест располагается в одном каталоге с тестируемым кодом; выделенный каталог для тестов не используется.
2. Тесты бизнес-логики размещаются во внешнем пакете `service_test` и обращаются исключительно к экспортированному интерфейсу, что допускает изменение внутренней реализации без правки тестов.
3. Общее состояние инициализируется через `suite`: метод `SetupTest` заново создаёт тестовые двойники и экземпляр сервиса, исключая взаимное влияние тестов.
4. Репозитории тестируются на действующих экземплярах СУБД, а не на двойниках драйвера: корректность сценариев Lua и SQL-выражений иным способом не подтверждается.
5. В тестовом окружении применяются те же миграции, что и в рабочем, вследствие чего расхождение схем исключено.
6. Утверждения формулируются относительно наблюдаемого поведения — итогового состояния, выделенного количества, состава обращений к зависимостям, — а не относительно внутренних полей структур.
7. Поведение при отказе внешних компонентов проверяется явно: для каждого сценария деградации подтверждается, что подтверждённая оплата не отменяется, а ошибка не распространяется на клиента.
8. В тестах транспортного слоя применяются ручные заглушки: предметом проверки является последовательность сообщений во времени, а не количество вызовов.

### 8.4. Вне области тестирования

- Сквозное тестирование пользовательского сценария;
- нагрузочное тестирование состязаний за последнюю единицу товара;
- контроль минимального покрытия в процессе непрерывной интеграции.

Сквозной сценарий проверяется коллекцией Postman (48 запросов, 70 утверждений), исполняемой посредством `newman`.

## 10. Ограничения реализации

Перечисленные ограничения являются следствием осознанных проектных решений и границ кейса.

- Аутентификация не реализована в соответствии с требованием `FR-D1`. Идентификатор пользователя передаётся клиентом и не подлежит проверке, вследствие чего защищённость права определяется защищённостью идентификатора.
- Платёжная функциональность не реализована в соответствии с требованием `FR-D2`. Факт оплаты сообщается заглушкой внешней системы.
- Пополнение остатка не поддерживается. Состояние `SOLD_OUT` является терминальным.
- Наименования товаров не передаются. Каталог принадлежит внешней системе; сопоставление идентификатора товара с его описанием выполняется клиентским приложением.
- Очистка ключей Redis не выполняется. Записи завершённых членств сохраняются без ограничения срока хранения.
- Валидация идентификаторов пользователя и товара не выполняется ни по длине, ни по составу допустимых символов.
