# Redis: конвенции и структуры

Redis не обладает схемой: любой ключ создаётся неявно первой же командой записи. Изложенное ниже представляет собой не объявление структуры хранилища, а договорённость, соблюдение которой обеспечивается исключительно кодом.

Реализация сосредоточена в единственном файле `backend/internal/repository/redis/cache.go`: там же объявлены сценарии Lua и построены все ключи. Вынесение построителей ключей в отдельный файл не выполнено — при текущем объёме (шесть семейств ключей, один потребитель) это не оправдано; при появлении второго потребителя решение подлежит пересмотру.

## 1. Конвенции именования ключей

- Разделитель частей ключа — двоеточие, схема `{resource}:{id}[:{sub-resource}]`. Нотация общепринята в экосистеме Redis и распознаётся средствами интроспекции: `redis-cli --scan`, группировка по дереву в RedisInsight.
- Имя ресурса указывается в единственном числе: `member:`, а не `members:`; `right:`, а не `rights:`. Исключением является ключ `expiring:rights`, обозначающий не отдельную сущность, а множество ожидающих обработки таймеров.
- Тип структуры в имени ключа не кодируется: он определяется командой `TYPE` во время исполнения, а дублирование расходится с действительностью при смене типа.
- Обозначения в настоящем документе: `{pid}` — `product_id`, `{uid}` — `user_id`, `{token}` — идентификатор права.
- Хеш-теги для размещения связанных ключей в одном слоте не применяются: развёртывание использует единственный экземпляр Redis. При переходе к кластеру ключи `queue:{pid}` и `stock:{pid}`, совместно обрабатываемые одним сценарием Lua, потребуют согласованного хеш-тега.

## 2. Структуры

### 2.1. Очередь FIFO

```
ZSET  queue:{pid}
  member = user_id
  score  = порядковый номер, получаемый командой INCR над queue:{pid}:seq
```

Вход: `INCR queue:{pid}:seq`, затем `ZADD queue:{pid} <seq> <user_id>`. Обе команды выполняются одним сценарием Lua.

Извлечение головы очереди совмещено с распределением остатка в сценарии `PopAndAllocate` (раздел 3). Точечное исключение участника выполняется командой `ZREM`.

Применён Sorted Set, а не List: требуется точечное исключение элемента из середины со сложностью `O(log n)`, чего List не обеспечивает без полного просмотра.

При аварии долговременного хранилища в момент продвижения участник возвращается в очередь командой `ZADD` с исходным порядковым номером, вследствие чего его позиция не ухудшается.

После истечения срока действия права участник переводится в терминальное состояние `DECLINED` и автоматически в очередь не возвращается.

### 2.2. Состояние членства

```
HASH  member:{pid}:{uid}
  product_id          -> идентификатор товара
  user_id             -> идентификатор пользователя
  status              -> QUEUED | RIGHT_ACTIVE | OFFER_PENDING | DECLINED | PURCHASED | SOLD_OUT
  quantity            -> запрошенное количество, целое
  available_quantity  -> предлагаемое количество; заполняется исключительно для OFFER_PENDING
  current_token       -> действующий идентификатор права; заполняется для RIGHT_ACTIVE
  expires_at          -> момент истечения срока, RFC 3339 с наносекундами
  created_at          -> момент создания членства, RFC 3339 с наносекундами
  updated_at          -> момент последнего изменения, RFC 3339 с наносекундами
```

Неприменимые поля записываются пустой строкой, а не удаляются: постоянный набор полей позволяет обновлять запись одной командой `HSET` без предварительного чтения.

Время сериализуется в формате RFC 3339 с наносекундами, а не меткой Unix: сохраняется точность до наносекунд, а значение остаётся пригодным к чтению при отладке. Метка Unix применяется исключительно там, где значение участвует в сравнении на стороне Redis, то есть в качестве веса в упорядоченных множествах.

Срок жизни ключа не устанавливается: запись существует, пока состояние не станет терминальным. Политика последующего удаления терминальных записей не определена, см. раздел 6.

Данная структура является источником состояния для чтения: конечная точка `GET /queue/{pid}/members/me` обслуживается из неё, а таблица `queue_memberships` в PostgreSQL хранит долговременную копию.

### 2.3. Право на покупку

```
HASH  right:{token}
  token, user_id, product_id, quantity
  status      -> ACTIVE | EXPIRED | USED
  order_id    -> заполняется при подтверждении оплаты
  created_at, expires_at, used_at
```

Читается первой при обработке `GET /rights/{token}`; при промахе запись восстанавливается из PostgreSQL и помещается обратно в кэш. Источником истины является таблица `rights` (`docs/storage/postgres.md`), настоящий ключ — исключительно ускоритель чтения.

### 2.4. Таймеры истечения сроков

```
ZSET  expiring:rights
  member = "{pid}:{uid}"
  score  = момент истечения срока, метка Unix в секундах
```

Механизм `EXPIRE` применяется в Redis к ключу целиком и неприменим к отдельным элементам упорядоченного множества либо хеша: истечение срока, записанного в поле, самостоятельно не обнаруживается. Настоящая структура представляет собой не таймер, а указатель для быстрого поиска просроченных элементов силами обработчика, описанного в разделе 4.

Множество является общим для всех товаров, а не разделённым по `{pid}`: обработчик выполняет единственный запрос за цикл независимо от числа товаров, а составной элемент `"{pid}:{uid}"` разбирается уже на стороне сервиса.

Для действующего права вес элемента устанавливается не в момент `expires_at` права, а в ближайший из двух моментов: истечение срока права либо исчерпание интервала подтверждения присутствия `RIGHT_HEARTBEAT_TIMEOUT`. Подтверждение присутствия клиента переносит вес вперёд сценарием `RefreshExpiryTimer`, который отказывает в продлении, если элемент уже просрочен, то есть заявлен обработчиком к обработке. Перенос выполняется исключительно вперёд, вследствие чего конкурентные подтверждения не сокращают срок.

### 2.5. Кэш остатка

```
HASH  stock:{pid}
  product_count    -> физический остаток; локальное зеркало значения AvitoBackend
  available_units  -> остаток за вычетом удерживаемого правами и предложениями
```

Инициализация выполняется при обработке входа в очередь: если ключ отсутствует, значение, полученное вызовом `GET /products/{pid}/stock` к AvitoBackend, записывается в оба поля. Условие отсутствия ключа проверяется внутри сценария Lua, вследствие чего конкурентные входы не переопределяют уже ведущийся учёт.

Поле с моментом синхронизации не ведётся: значение не используется ни одним потребителем, а долговременная копия остатка с меткой времени хранится в таблице `product_stock`.

### 2.6. Публикация событий

```
CHANNEL updates:{pid}:{uid}      -- изменение состояния конкретного участника
CHANNEL queue-updates:{pid}      -- изменение очереди либо остатка товара
```

Публикуемое сообщение является **сигналом инвалидации**, а не представлением состояния: в канал участника передаётся объект вида `{"status":"..."}`, в канал товара — постоянная строка. Получив сигнал, обработчик соединения повторно читает текущее состояние членства и позицию в очереди и передаёт клиенту фактическое представление, соответствующее ответу `GET /queue/{pid}/members/me`.

Такое разделение принято намеренно. Публикация готового представления потребовала бы вычислять его в момент изменения для каждого получателя, включая позицию в очереди, зависящую от состояния соседей; при конкурентных изменениях клиент мог бы получить устаревшее представление, опередившее актуальное. Повторное чтение по сигналу устраняет обе трудности ценой одного дополнительного обращения к Redis.

Обработчик соединения подписывается одновременно на оба канала: изменение чужого членства влияет на позицию и прогноз ожидания данного участника, вследствие чего канал товара необходим наравне с персональным.

Передача клиенту выполняется исключительно при фактическом изменении представления: перед отправкой оно сравнивается с ранее переданным. При переходе в терминальное состояние соединение закрывается сервером.

## 3. Сценарии Lua

Сценарий Lua исполняется Redis атомарно и однопоточно: до его завершения ни одна другая команда, в том числе от другого экземпляра сервиса, не может вклиниться между внутренними шагами. Это отличается от `MULTI/EXEC`, который обеспечивает непрерываемое исполнение заранее заданного перечня команд, но не допускает ветвления по прочитанному значению. Сценарий Lua позволяет выразить последовательность «прочитать `available_units`, при достаточности списать и сообщить об успехе, иначе сообщить об отказе» единым неделимым действием.

Это обязательно для операций, в которых два конкурентных запроса иначе наблюдали бы одно и то же значение до того, как один из них его изменит, то есть ровно для задачи, поставленной кейсом.

Применяемые сценарии:

| Сценарий | Назначение |
| --- | --- |
| `InitStock` | Запись исходного остатка при отсутствии ключа |
| `TryAllocate` | Проверка `available_units` и удержание запрошенного либо доступного количества |
| `Enqueue` | Присвоение порядкового номера и помещение участника в очередь |
| `RemoveFromQueue` | Исключение участника из очереди |
| `RestoreAvailableUnits` | Возврат удержанного количества в пул |
| `Requeue` | Возврат участника в очередь с исходным порядковым номером |
| `PopAndAllocate` | Чтение головы очереди, проверка состояния участника, исключение и распределение количества |
| `GetAndRemoveExpired` | Чтение и снятие просроченных таймеров |
| `RefreshExpiryTimer` | Перенос таймера вперёд при подтверждении присутствия клиента |

Каждый сценарий, изменяющий очередь либо остаток, публикует сигнал в канал `queue-updates:{pid}` в пределах того же атомарного исполнения: подписчик не может наблюдать состояние, о котором ещё не получил уведомления.

Сценарий `PopAndAllocate` возвращает не только распределённое количество, но и вычисленное состояние участника, а также его исходный порядковый номер — последний необходим для возврата участника в очередь при аварии долговременного хранилища.

Именно сценарии Lua являются единственным местом системы, где физически предотвращается двойная выдача одной единицы товара. PostgreSQL в этот момент не участвует и лишь фиксирует уже принятое решение (`docs/storage/postgres.md`, раздел «Разграничение гарантий»).

Сценарии объявлены константами `redis.NewScript` в `backend/internal/repository/redis/cache.go`, а не отдельными файлами `.lua`. Библиотека `go-redis` исполняет их командой `EVALSHA`, а при отсутствии сценария в кэше сервера самостоятельно выполняет `EVAL`, вследствие чего явная загрузка при запуске не требуется. Размещение рядом с вызывающим кодом принято намеренно: сценарий и разбор его результата изменяются совместно, а разнесение по разным файлам допускает их рассогласование.

## 4. Обработчик истечения сроков

Отдельный компонент сервиса, исполняемый горутиной внутри процесса прикладного интерфейса. Периодичность задаётся параметром `EXPIRATION_INTERVAL`, значение по умолчанию — одна секунда.

Порядок работы на каждом цикле:

1. Сценарием `GetAndRemoveExpired` прочитать и одновременно снять элементы `expiring:rights` с весом, не превышающим текущий момент. Чтение и снятие выполняются атомарно, что исключает повторную обработку одного элемента конкурентными экземплярами.
2. Для каждого элемента `{pid}:{uid}` прочитать состояние членства и выполнить переход:
   - для состояния `RIGHT_ACTIVE` — одной транзакцией PostgreSQL перевести право в `EXPIRED` и зафиксировать терминальное состояние членства `DECLINED`, после чего обновить кэш, вернуть удерживаемое количество в пул и продвинуть очередь;
   - для состояния `OFFER_PENDING` — зафиксировать терминальное состояние `DECLINED`, вернуть предложенное количество в пул и продвинуть очередь;
   - для прочих состояний обработка не производится: пользователь уже завершил оплату либо отказался самостоятельно, вследствие чего таймер утратил актуальность.
3. Опубликовать изменение состояния в канал участника.

Поскольку снятие таймера предшествует обработке, сбой на шаге 2 привёл бы к утрате перехода. Для устранения этого элемент возвращается в множество с задержкой в одну секунду при недоступности состояния членства либо при неудаче записи в долговременное хранилище. Возврат не выполняется, если переход отвергнут по причине несоответствия состояния: повторная попытка привела бы к тому же результату.

Логику необходимо реализовывать явно: Redis самостоятельно её не исполняет, а структура раздела 2.4 является указателем для поиска просроченных элементов, а не таймером с обратным вызовом.

## 5. Отказоустойчивость

Развёртывание использует режим `appendonly yes`, вследствие чего содержимое кэша переживает перезапуск контейнера. На это свойство логика не опирается: при утрате ключа состояние восстанавливается из PostgreSQL, являющегося источником истины.

Порядок записи фиксирован: сначала долговременное хранилище, затем кэш. Обоснование и разбор аварийных интервалов приведены в `docs/storage/postgres.md`.

## 6. Открытые вопросы

- Политика удаления терминальных записей `member:{pid}:{uid}`, то есть срок жизни после перехода в `PURCHASED`, `DECLINED` либо `SOLD_OUT`. Для демонстрации несущественна, подлежит определению до продолжительной эксплуатации.
- Потребность в кластере Redis и разделении по хеш-тегу (раздел 1). При текущем масштабе неактуальна, оставлена как задел.
