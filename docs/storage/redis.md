# Redis: конвенции и структуры

Redis не имеет схемы (нет DDL) — любой ключ создаётся неявно первой же командой записи. Всё,
что описано ниже — не объявление структуры БД, а **договорённость**, которую код обязан
соблюдать вручную.

Держите константы/билдеры ключей (`queue:%s`, `member:%s:%s` и т.п.) в одном месте кода
(например, `internal/storage/redis/keys.go`), а не собирайте строки конкатенацией по всему
проекту — иначе конвенция ниже быстро разъедется с реальностью.

## 1. Конвенции именования ключей

- Разделитель — `:` между частями ключа, схема `{resource}:{id}[:{sub-resource}[:{sub-id}]]`.
  Общепринятая нотация в экосистеме Redis: понимается инструментами интроспекции
  (`redis-cli --scan`, RedisInsight умеет группировать ключи по `:` как по дереву).
- Имя ресурса — **в единственном числе** (`member:`, не `members:`; `right:`, не `rights:`).
- Тип структуры **не** кодируется в имени ключа (не `queue:zset:{pid}`) — тип и так виден через
  `TYPE key` в рантайме, дублирование избыточно и рискует разойтись при смене типа структуры.
- Плейсхолдеры в этом документе: `{pid}` — `product_id`, `{uid}` — `user_id`, `{token}` — токен
  права.
- Если когда-нибудь понадобится Redis Cluster — ключи, которые обязаны попасть в один слот
  (например, `queue:{42}` и `stock:{42}` для одного товара, чтобы Lua-скрипт мог работать с
  обоими в одной операции), помечаются хеш-тегом: `queue:{42}` вместо `queue:42`. Для текущего
  единственного инстанса это не требуется, но закладывать в имена сразу — дёшево и убережёт от
  переименования всех ключей при масштабировании.

## 2. Структуры

### 2.1 FIFO-очередь
```
ZSET  queue:{pid}
  member = user_id
  score  = порядковый номер (monotonic), из INCR queue:{pid}:seq
```
- Вход: `INCR queue:{pid}:seq` → `ZADD queue:{pid} <seq> <user_id>`.
- Следующий в очереди: `ZRANGE queue:{pid} 0 0`.
- Выход/отказ/requeue: `ZREM queue:{pid} <user_id>`. Requeue после истечения `RIGHT_ACTIVE`
  (design_context.md, п.4) — это `ZREM` + новый `INCR`/`ZADD` с бо́льшим score, т.е. **в конец**,
  не в начало (иначе бездействие одного пользователя блокирует остальных навсегда).

Sorted Set, а не List — нужна точечная отмена элемента из середины (`ZREM`, O(log n)),
чего List не даёт без сканирования всего списка.

### 2.2 Статус членства (то, что отдаёт `GET /queue/{pid}/members/me`)
```
HASH  member:{pid}:{uid}
  status              -> QUEUED | RIGHT_ACTIVE | OFFER_PENDING | DECLINED | PURCHASED | SOLD_OUT
  quantity            -> запрошенное количество (int)
  available_quantity  -> заполнено только для OFFER_PENDING (int)
  token               -> текущий токен, если RIGHT_ACTIVE (иначе пусто)
  expires_at          -> unix ts, если применимо
  updated_at          -> unix ts
```
Без TTL на ключ целиком — живёт, пока состояние не станет терминальным (`PURCHASED`/`DECLINED`/
`SOLD_OUT`). Политика последующей очистки терминальных записей — открытый вопрос, см. §5.

### 2.3 Право на покупку (кэш перед Postgres)
```
HASH  right:{token}
  user_id, product_id, quantity, status (ACTIVE|EXPIRED|USED), expires_at, order_id
```
Читается первым при `GET /rights/{token}`; при промахе — читаем Postgres и восстанавливаем этот
кэш. Postgres (таблица `rights`, см. `docs/storage/postgres.md`) — источник истины; этот ключ —
только ускоритель чтения.

### 2.4 Таймеры истечения права/предложения
```
ZSET  expiring:rights
  member = "{pid}:{uid}"
  score  = expires_at (unix ts)
```
Важно: `EXPIRE`/TTL в Redis применяется только к **целым ключам**, а не к отдельным элементам
внутри ZSet/Hash — Redis сам не «заметит», что чей-то `expires_at` прошёл. Эта структура — не
автоматический механизм, а просто индекс для быстрого поиска просроченных элементов силами
отдельного фонового процесса. Требования к этому процессу — см. §4.

### 2.5 Кэш остатка от AvitoBackend
```
HASH  stock:{pid}
  product_count     -> int, кэш от AvitoBackend (design_context.md §7.1)
  available_units   -> int, product_count минус то, что заморожено активными правами/предложениями
  synced_at         -> unix ts последней синхронизации
```
Инициализация: при первом `POST /queue/{pid}/members` для товара, если `EXISTS stock:{pid} == 0`
— запросить `GET /products/{pid}/stock` у AvitoBackend и сделать `HSET`.

### 2.6 Realtime push (WebSocket)
```
CHANNEL updates:{pid}:{uid}
```
Публикуется JSON, соответствующий телу ответа `GET /me` (см. `docs/api.yml`, схемы
`RightActive`/`OfferPending`/`Queued`/`SoldOut`/`Declined`/`Purchased`). WS-хендлер на входящем
соединении делает `SUBSCRIBE updates:{pid}:{uid}` и форвардит сообщения в сокет без изменений.

## 3. Lua-скрипты: зачем и как

Lua-скрипт в Redis выполняется **атомарно и однопоточно** — пока он не завершится, ни одна
другая команда (в т.ч. от другой горутины/инстанса сервиса) не может вклиниться между его
внутренними шагами. Это не то же самое, что `MULTI/EXEC`: `MULTI/EXEC` гарантирует
непрерываемое выполнение заранее заданного списка команд, но **не позволяет ветвиться** на
основе прочитанного значения (нет `if` на сервере). Lua-скрипт — полноценный код с условиями,
поэтому им можно выразить «прочитать `available_units` → **если** хватает → списать и вернуть
success → **иначе** вернуть failure» одним неделимым действием.

Это обязательно для операций, где два конкурентных запроса могут иначе увидеть одно и то же
значение до того, как один из них его изменит (ровно та проблема, которую просит решить кейс —
не продать одну единицу дважды):

- проверка `available_units` + выдача/заморозка права (`TryAllocate`, п.2 design_context.md);
- decrement `product_count`/`available_units` после `payment_succeeded`.

Это единственное место во всей системе, где физически предотвращается двойная выдача одной и
той же единицы товара — Postgres в этот момент ещё не участвует, он лишь durable-фиксирует уже
принятое здесь решение (см. `docs/storage/postgres.md`, раздел «Важно: это не распределённая
транзакция»).

Набросок сути (не финальная реализация — детали вроде частичной выдачи, работы с несколькими
полями хэша и форматом ошибок решаются при разработке вместе с вызывающим Go-кодом):

```lua
-- TryAllocate(product_id, qty)
-- KEYS[1] = stock:{pid}
-- ARGV[1] = qty
local available = tonumber(redis.call('HGET', KEYS[1], 'available_units'))
if available >= tonumber(ARGV[1]) then
    redis.call('HINCRBY', KEYS[1], 'available_units', -ARGV[1])
    return 1  -- allocated
else
    return 0  -- not enough
end
```

Практика в коде: скрипты — отдельные `.lua`-файлы (например,
`internal/storage/redis/scripts/*.lua`), не строки, встроенные в Go-код. При старте сервиса —
`SCRIPT LOAD` каждого файла (Redis возвращает SHA1), дальше вызывать `EVALSHA`. Библиотека
`go-redis` инкапсулирует это через `redis.NewScript(...).Run(ctx, client, keys, args...)` —
сама делает `EVALSHA`, а при промахе кэша скриптов на сервере — fallback на `EVAL`.

## 4. Фоновый воркер (expiry worker)

Отдельный компонент сервиса, не часть Redis. Обязанности:

1. Каждый тик (например, `time.NewTicker(1 * time.Second)`) — `ZRANGEBYSCORE expiring:rights
   0 <now>`, где `<now>` — текущий unix ts.
2. Для каждого просроченного `{pid}:{uid}` — выполнить бизнес-логику истечения:
   - `right:{token}.status = EXPIRED` (и в Postgres — см. `postgres.md`);
   - обновить `member:{pid}:{uid}` → `QUEUED`;
   - requeue в конец `queue:{pid}` (§2.1);
   - `PUBLISH updates:{pid}:{uid}` с новым статусом.
3. `ZREM expiring:rights {pid}:{uid}` — снять с таймера обработанный элемент, чтобы не
   обработать повторно на следующем тике.

Это нужно реализовать явно — Redis не запускает эту логику сам, ZSet из §2.4 — это только
удобная структура для поиска «что просрочено», а не таймер с колбэком.

## 5. Открытые вопросы

- Политика эвикции терминальных `member:{pid}:{uid}` (TTL после `PURCHASED`/`DECLINED`/
  `SOLD_OUT`) — не критично для демо на хакатоне, стоит решить перед долгоживущим прод-деплоем.
- Нужен ли Redis Cluster / шардинг по хеш-тегу (§1) — не актуально при текущем масштабе кейса,
  оставлено как задел на будущее.
