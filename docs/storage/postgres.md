# PostgreSQL: назначение таблиц

Определения схемы приведены в каталоге `backend/internal/migrations/` и являются источником истины. Миграции встроены в исполняемый файл средствами `embed` и применяются автоматически при инициализации сервиса средствами `goose`. Настоящий документ не воспроизводит SQL, а поясняет назначение каждой таблицы и её соотношение со структурами Redis (`docs/storage/redis.md`). При расхождении настоящего текста с миграциями верными следует считать миграции.

PostgreSQL не обслуживает ни аналитику, ни горячий путь чтения. Его назначение — долговременная фиксация того, что должно пережить перезапуск Redis и допускать проверку: финансово значимых событий и текущего состояния членства, необходимого сопровождению. Логика очереди и распределения остатка, требующая устойчивости к состязанию, размещена в Redis.

## 1. Таблицы

### 1.1. `rights`

Одна строка на каждое выданное право. Историчность сохраняется: у одной пары `(user_id, product_id)` со временем может накопиться несколько строк, поскольку после истечения срока пользователь вправе повторно войти в очередь и получить новое право.

Ключевые поля: `token` — первичный ключ, `user_id`, `product_id`, `quantity`, `status` (перечисление `ACTIVE`, `EXPIRED`, `USED`), `order_id` — заполняется исключительно при подтверждении оплаты, `expires_at`, `used_at`.

Таблица является источником истины по правам; хеш Redis `right:{token}` (`redis.md`, раздел 2.3) представляет собой кэш поверх неё.

### 1.2. `queue_memberships`

Долговременная копия **текущего** состояния членства пользователя в очереди на товар, то есть того же, что возвращает `GET /queue/{pid}/members/me` и что кэшируется в Redis как `member:{pid}:{uid}` (`redis.md`, раздел 2.2).

Таблица обновляется вставкой с разрешением конфликта: ограничение уникальности по паре `(product_id, user_id)` обеспечивает соответствие «одна строка — одно текущее состояние», а не журнал событий. Ограничение выполняет двойную роль: помимо целостности данных, оно поддерживает идемпотентность повторного входа в очередь (`docs/design_context.md`, п. 5.3).

Назначение таблицы состоит в том, чтобы после перезапуска либо отказа Redis не требовалось восстанавливать состояние каждого пользователя вручную, а сопровождение имело возможность наблюдать состояние без обращения к кэшу.

### 1.3. `product_stock`

Долговременное зеркало остатка, полученного от AvitoBackend; источником истины по физическому остатку является сама внешняя система (`design_context.md`, п. 9). Хеш Redis `stock:{pid}` (`redis.md`, раздел 2.5) — кэш поверх этой таблицы, обеспечивающий атомарное распределение.

Поля: `product_id` — первичный ключ, `product_count` — текущий остаток с ограничением неотрицательности, `total_stock` — исходное значение на момент первичной инициализации, `updated_at`.

Первичная запись выполняется вставкой с разрешением конфликта в пользу существующей строки: повторный вход в очередь по уже известному товару не переопределяет ведущийся учёт значением, повторно прочитанным у внешней системы.

Хранение остатка отдельно от AvitoBackend избавляет от повторного сетевого запроса по каждому уже обработанному товару после перезапуска Redis.

## 2. Индексы

Текущий состав индексов и обслуживаемые ими пути чтения:

| Индекс | Таблица | Обслуживаемый путь |
| --- | --- | --- |
| `rights_pkey` (`token`) | `rights` | Проверка права: `GET /rights/{token}` |
| `idx_rights_user_product` | `rights` | Выборка прав пользователя по товару |
| `idx_rights_product` | `rights` | Выборка прав по товару |
| Уникальный по `(product_id, user_id)` | `queue_memberships` | Чтение и обновление членства: `GET /queue/{pid}/members/me` |
| `idx_queue_memberships_user` (`user_id`) | `queue_memberships` | Перечень очередей пользователя: `GET /me/queues` |

Индекс по `user_id` добавлен отдельной миграцией одновременно с появлением экрана «Мои очереди»: уникальный индекс по паре начинается с `product_id` и выборку по одному лишь пользователю не обслуживает.

Индексы по `created_at` для отчётных запросов заранее не создаются: они подлежат добавлению отдельной миграцией по факту появления соответствующей потребности.

## 3. Порядок операций записи

Порядок фиксирован: **сначала PostgreSQL, затем Redis**. Это исключает расхождение кэша с долговременным хранилищем при аварийном завершении процесса между двумя записями.

1. **Выдача права.** Вставка в `rights` с фиксацией транзакции, затем запись `right:{token}`, затем `member:{pid}:{uid}`, затем помещение элемента в `expiring:rights`.
2. **Подтверждение оплаты.** Одной транзакцией: перевод права в `USED` с фиксацией `order_id` и `used_at`, уменьшение `product_count` в `product_stock`. После фиксации — обновление `stock:{pid}` и `member:{pid}:{uid}`, снятие таймера и публикация события.
3. **Истечение срока действия права.** Одной транзакцией: перевод права в `EXPIRED` и запись терминального состояния членства. После фиксации — обновление кэша, возврат удерживаемого количества в пул и продвижение очереди.

При аварийном завершении процесса между шагами ключ Redis при последующем чтении либо отсутствует, либо содержит устаревшее значение, вследствие чего код обязан перечитать PostgreSQL и восстановить кэш. Обратный порядок создавал бы интервал, в течение которого кэш содержит решение, отсутствующее в долговременном хранилище: при аварии в этом интервале решение утрачивалось бы безвозвратно, а кэш продолжал бы сообщать недостоверные сведения.

## 4. Разграничение гарантий

Двухфазная фиксация между Redis и PostgreSQL **не применяется**. Это две независимые системы, синхронизация между которыми не атомарна как единое целое. Различные гарантии обеспечиваются различными механизмами, и их не следует отождествлять.

- **Устойчивость к состязанию за последнюю единицу**, то есть недопустимость выдачи двум пользователям права на одну и ту же единицу, физически обеспечивается сценарием Lua в Redis (`redis.md`, раздел 3): решение принимается в момент атомарной проверки `available_units`. PostgreSQL в этот момент не участвует.
- **Сохранность решения**, то есть недопустимость утраты выданного права при отказе процесса либо Redis, обеспечивается PostgreSQL. Запись выполняется после того, как решение принято.

Полная последовательность выдачи права: сценарий Lua необратимо удерживает единицы в `available_units`; выполняется вставка в `rights`; обновляются хеши Redis.

Аварийное завершение между первым и вторым шагами приводит к тому, что единица помечена удержанной в Redis, при этом соответствующее право отсутствует и в PostgreSQL, и в кэше. Итогом является временная недоступность этой единицы. Следовательно, **в редком случае система способна недопродать одну единицу, но не способна продать её дважды**.

Компромисс асимметричен намеренно. Любой отказ в указанном интервале разрешается в сторону недопродажи, что допустимо, поскольку восполнение остатка находится вне области MVP, а не в сторону перепродажи, прямо запрещённой условиями кейса (`design_context.md`, п. 2, требование 2). Двухфазная фиксация устранила бы и этот интервал ценой производительности, не оправданной для настоящей задачи.

## 5. Транзакции внутри PostgreSQL

Независимо от межсистемной последовательности, операции, изменяющие сразу право и остаток, выполняются настоящей транзакцией ACID.

**Подтверждение оплаты.** Строка права блокируется на чтение с последующим изменением, что исключает параллельную обработку одного и того же уведомления. Перевод в `USED` выполняется с условием текущего состояния `ACTIVE`, а уменьшение остатка — с условием его достаточности. Невыполнение любого из условий отменяет транзакцию целиком: право не может оказаться помеченным использованным без соответствующего уменьшения остатка, и наоборот. Недостаточность остатка возвращается как исчерпание товара, что составляет последний рубеж защиты от перепродажи на случай расхождения кэша с долговременным хранилищем.

**Истечение срока действия права.** Перевод в `EXPIRED` также выполняется с условием текущего состояния `ACTIVE` и в той же транзакции, что и запись терминального состояния членства. Транзакция сообщает вызывающей стороне, был ли переход фактически совершён: удерживаемое количество возвращается в пул исключительно той операцией, которая его совершила. Это исключает двойной возврат при состязании обработчика истечения сроков с явным отказом пользователя.

Повторная обработка ранее учтённого уведомления об оплате распознаётся по текущему состоянию права и завершается без внешних воздействий, что обеспечивает идемпотентность служебной конечной точки.

## 6. Открытые вопросы

- Потребность в отдельной таблице событий очереди, доступной только для добавления, то есть журнала входов, предложений, отказов, истечений и покупок, для полного разбора состязаний. В текущие миграции не входит; подлежит добавлению отдельной миграцией при появлении конкретной потребности.
- Политика удаления завершённых членств и прав по истечении длительного срока. Для демонстрации несущественна.
