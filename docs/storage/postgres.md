# Postgres: назначение таблиц

Актуальный DDL — в `migrations/` (источник истины, применяется миграциями), этот файл не
дублирует SQL, а объясняет **зачем** каждая таблица нужна и как она соотносится со структурами
Redis (`docs/storage/redis.md`). Если этот текст разошёлся с миграциями — миграции правы.

Postgres здесь не для аналитики и не для hot-path чтения — это durable-журнал для того, что
должно пережить рестарт Redis и быть аудируемым (финансово значимые события, текущее состояние
членства для саппорта). Логика очереди/allocation (быстрая, под конкуренцию) живёт в Redis, см.
таблицу «кто за что отвечает» в `docs/design_context.md` (раздел про хранилище, если добавлен)
или напрямую в `docs/storage/redis.md`.

## Таблицы

### `rights`
Одна строка на каждый выданный токен права (историчность: у одного `(user_id, product_id)` со
временем может накопиться несколько строк — например, после истечения пользователь может
заново войти в очередь и позднее получить новый токен). Это источник истины по правам —
Redis-хэш `right:{token}` (см. `redis.md`, §2.3) —
только кэш поверх неё.

Ключевые поля: `token` (PK), `user_id`, `product_id`, `quantity`, `status`
(`ACTIVE`/`EXPIRED`/`USED`), `order_id` (заполняется только при `payment_succeeded`),
`expires_at`, `used_at`.

### `queue_memberships`
Durable-копия **текущего** статуса членства пользователя в очереди на товар — то же самое, что
отдаёт `GET /queue/{pid}/members/me` и что кэшируется в Redis как `member:{pid}:{uid}`
(`redis.md`, §2.2). Это upsert-таблица: уникальность по `(product_id, user_id)`, одна строка —
одно текущее состояние, а не лог событий. Нужна, чтобы после падения/рестарта Redis не
приходилось восстанавливать статус каждого пользователя вручную и чтобы саппорт/дебаг мог
посмотреть состояние без похода в Redis.

### `product_stock`
Durable-зеркало остатка, полученного от AvitoBackend (источник истины по физическому остатку —
сам AvitoBackend, вне нашей БД, см. `design_context.md` §7.1). Redis-хэш `stock:{pid}`
(`redis.md`, §2.5) — кэш поверх этой таблицы для быстрого атомарного decrement. Хранится
отдельно от AvitoBackend, чтобы при рестарте Redis не приходилось заново запрашивать остаток по
сети для каждого товара, с которым уже работали.

## Порядок записи: сначала Postgres, потом Redis

Чтобы Redis-кэш не разошёлся с Postgres при падении процесса между двумя записями, порядок
всегда фиксированный — **сначала Postgres (commit), потом Redis**:

1. Выдача права: `INSERT INTO rights` (commit) → `HSET right:{token}` → `HSET
   member:{pid}:{uid}` → `ZADD expiring:rights`.
2. `payment_succeeded`: одной транзакцией `UPDATE rights SET status='USED', order_id=...` +
   `UPDATE product_stock SET product_count = product_count - quantity` (commit) → обновить
   Redis (`stock:{pid}`, `member:{pid}:{uid}`) → `PUBLISH updates:{pid}:{uid}`.

Если процесс падает между шагами — при следующем чтении Redis-ключа он либо отсутствует, либо
устарел, и код обязан на этот случай перечитать Postgres и восстановить кэш. Обратный порядок
(сначала Redis) создал бы окно, где Redis показывает решение, которого ещё нет в durable-
хранилище — при краше в этом окне решение терялось бы безвозвратно, а Redis продолжал бы врать.

### Важно: это не распределённая транзакция (не 2PC), и это осознанно

Между Redis и Postgres **нет** двухфазного коммита — это две независимые системы, синхронизация
между ними не атомарна как единое целое. За разные гарантии отвечают разные механизмы, и их
нельзя путать:

- **Гонку конкурентных запросов на последнюю единицу** (не выдать двум пользователям право на
  одну и ту же единицу товара) физически предотвращает **Redis Lua-скрипт** (`redis.md`, §3) —
  именно там, в момент атомарной проверки `available_units`, происходит решение. Postgres в этот
  момент ещё не участвует.
- **Durability решения** (чтобы выданное право не пропало при падении процесса/Redis)
  обеспечивает **Postgres** (WAL) — запись туда происходит уже после того, как Redis принял
  решение.

Полная последовательность выдачи права: (1) Redis Lua атомарно резервирует `available_units` —
необратимое решение; (2) `INSERT INTO rights` в Postgres; (3) обновление Redis-хэшей
(`right:{token}`, `member:{pid}:{uid}`).

Если процесс падает **между шагом (1) и (2)** — единица уже помечена занятой в Redis, но токена
по ней ни в Postgres, ни толком в Redis нет. Итог такого падения — эта единица становится
временно недоступной ("зависшей"), т.е. **система в редком случае может недопродать одну
единицу, но никогда не продаст её дважды**. Это осознанный асимметричный компромисс: любой сбой
в этом узком окне резолвится в сторону "недопродать" — что допустимо (рестокинг всё равно вне
скоупа), а не в сторону "перепродать" — что прямо запрещено условиями кейса (см.
`design_context.md`, требование 2). Полноценный 2PC между Redis и Postgres убрал бы даже это
редкое окно, но обошёлся бы производительностью, которая для этой задачи не оправдана — выбор
сделан осознанно в пользу скорости, раз риск асимметричен и допустим.

Отдельно от этой межсистемной последовательности — на шаге подтверждения оплаты внутри самого
Postgres используется настоящая ACID-транзакция (`UPDATE rights SET status='USED' ...` +
`UPDATE product_stock SET product_count = product_count - quantity` одной транзакцией) — право
не может оказаться помеченным использованным без соответствующего списания остатка, и наоборот.

## Открытые вопросы

- Нужен ли отдельный append-only `queue_events` (лог всех событий: вход в очередь, offer,
  decline, expire, purchase) для полного аудита гонок — не входит в текущую миграцию, добавить
  отдельной миграцией при появлении конкретной потребности от жюри/саппорта.
- Индексы в текущей миграции — по `(user_id, product_id)` и `product_id` в `rights`, для
  `queue_memberships` уникальный индекс `(product_id, user_id)` уже покрывает основной путь
  чтения (`GET /me`). Если появятся отчётные запросы (например, «сколько прав выдано за
  период») — индексы по `created_at` добавить отдельной миграцией по факту потребности, не
  заранее.
