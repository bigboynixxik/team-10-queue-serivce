## 2. Предметная задача

Товар обладает ограниченным остатком, при этом несколько покупателей способны одновременно дойти до оплаты, а приобрести товар может лишь часть из них, поскольку оплата выполняется асинхронно. Требуется сервис очереди, который:

1. помещает пользователя в очередь до перехода к оформлению заказа;
2. исключает продажу одной единицы нескольким покупателям;
3. исключает обход очереди, то есть переход к покупке без действующего права;
4. предоставляет пользователю однозначные состояния без неопределённости;
5. встраивается в существующий сценарий покупки на платформе.

За пределами области кейса, то есть считается уже реализованным внешней системой: регистрация и авторизация, оформление заказа, проведение оплаты, хранение физического остатка товара.

## 3. Терминология

- **Queue Service (QS)** — разрабатываемая серверная часть.
- **AvitoBackend (AB)** — внешняя система Авито, инкапсулирующая условно существующие интерфейсы: оформление заказа, оплату, данные о товаре и его остатке. Находится вне области кейса; в репозитории замещена компонентом `backend/cmd/avitomock`. Queue Service выступает по отношению к ней клиентом двух конечных точек: получение остатка и уведомление о его уменьшении (пп. 8 и 9).
- **`product_count`** — физический остаток товара. Источником истины по этому значению является AvitoBackend; Queue Service ведёт локальное зеркало, инициализируемое вызовом `GET /products/{product_id}/stock` и уменьшаемое после каждой оплаты. Зеркало необходимо для атомарного распределения остатка без синхронного обращения к внешней системе на каждое решение.
- **`available_units`** — число единиц, свободных для выдачи в текущий момент, то есть остаток за вычетом удерживаемого действующими правами и предложениями. Справедливо соотношение `available_units <= product_count`.
- **Право на покупку** — временное, персональное, непередаваемое разрешение приобрести определённое количество товара до наступления `expires_at`.
- **Очередь FIFO** — единственная применяемая политика справедливости.

## 4. Модель права на покупку

Право описывается полями `token`, `user_id`, `product_id`, `quantity`, `status` (внутренние значения `ACTIVE`, `EXPIRED`, `USED`), `order_id`, `created_at`, `expires_at`, `used_at`.

Идентификатор права представляет собой непрозрачное значение UUID и не содержит кодированных данных. Принадлежность устанавливается посредством поиска: по предъявленному значению извлекается запись права, после чего её поле `user_id` сравнивается с идентификатором обратившегося. Отсутствие данных внутри идентификатора исключает как подделку, так и потребность в криптографической подписи, что удовлетворяет требованиям `FR-B2`, `FR-B4` и `NFR-4`.

Проверка выполняется по `user_id`, привязанному к учётной записи, а не к сессии либо устройству: в противном случае право допускало бы передачу другому лицу через совместное использование сессии.

## 5. Предметная логика

### 5.1. Точка входа

Пользователь находится на странице товара и нажимает кнопку покупки. Отдельный экран выбора количества до входа в очередь не предусмотрен: количество указывается непосредственно в запросе `POST /queue/{product_id}/members`.

### 5.2. Решение при входе в очередь

При обращении с указанным `quantity` возможны четыре исхода:

| Условие | Состояние | Содержание |
| --- | --- | --- |
| `available_units >= quantity` | `RIGHT_ACTIVE` | Право выдано на всё запрошенное количество; экран ожидания не отображается |
| `0 < available_units < quantity` | `OFFER_PENDING` | Доступно меньше запрошенного; выдаётся частичное предложение с полем `available_quantity` |
| `available_units == 0`, `product_count > 0` | `QUEUED` | Помещение в конец очереди FIFO |
| `product_count == 0` | `SOLD_OUT`, код `409` | Товар исчерпан, освобождение единиц не предвидится |

Решение принимается сценарием Lua в Redis как единственная атомарная операция над `stock:{product_id}`. Проверка пустоты очереди в это решение не входит: удерживаемые единицы уже вычтены из `available_units`, вследствие чего ожидающий участник по определению не имеет закреплённого за собой количества. Продвижение очереди выполняется отдельно, при каждом возврате единиц в пул (п. 5.6).

Состояние `OFFER_PENDING` достижимо как непосредственно при входе, так и позднее, посредством сообщения по каналу реального времени, когда очередь дошла до участника, а освободившееся количество оказалось меньше изначально запрошенного.

Верхняя граница `quantity` не проверяется. Запрос, превышающий физический остаток, приводит к частичному предложению либо к постановке в очередь, то есть обрабатывается штатной логикой распределения. Отклоняется кодом `400` исключительно значение, меньшее либо равное нулю.

### 5.3. Идемпотентность повторного входа

При наличии у пользователя действующего членства (`QUEUED`, `RIGHT_ACTIVE`, `OFFER_PENDING`) повторный вызов `POST /queue/{product_id}/members` возвращает текущее состояние без изменений: новая запись не создаётся, `quantity` не пересчитывается. Это позволяет клиентскому приложению безопасно повторять запрос при двойном нажатии либо сетевом сбое, не создавая пользователю вторую позицию в очереди на тот же товар.

Уникальность обеспечивается на уровне схемы: таблица `queue_memberships` содержит ограничение уникальности по паре `(product_id, user_id)`.

### 5.4. Реакция на частичное предложение

Пользователь обязан отреагировать до истечения срока предложения (`OFFER_TTL`):

- **Принятие меньшего количества** — `PATCH /queue/{product_id}/members/me` со значением от единицы до `available_quantity`. Членство переводится в `RIGHT_ACTIVE`, выдаётся новое право. Неиспользованный остаток немедленно возвращается в пул, после чего очередь продвигается: если возвращённого количества достаточно следующему участнику, он получает право либо предложение без дополнительного ожидания.
- **Отказ** — `DELETE /queue/{product_id}/members/me`. Возвращается код `204`, членство переводится в терминальное состояние `DECLINED`, удержанное количество полностью возвращается в пул.
- **Бездействие до истечения срока** — предложение снимается фоновым обработчиком, что эквивалентно явному отказу: терминальное состояние `DECLINED`, возврат количества в пул, уведомление по каналу реального времени.

### 5.5. Истечение срока действия права

Если обладатель права не завершает оплату до наступления `expires_at`, выполняется единственный допустимый неоплаченный терминальный переход:

- право переводится в состояние `EXPIRED`; наружу как отдельное состояние оно не передаётся;
- членство переводится в терминальное состояние `DECLINED` с очисткой полей `current_token` и `expires_at`; пользователю направляется соответствующее уведомление;
- удерживаемое количество возвращается в пул и распределяется следующему участнику очереди по логике п. 5.2;
- автоматический возврат пользователя в очередь не производится: для новой попытки требуется повторный вход, при этом прежнее право сохраняет состояние `EXPIRED`.

Перевод права в `EXPIRED` и запись терминального состояния членства выполняются одной транзакцией PostgreSQL. Исход конкурентных операций определяется этой транзакцией: возврат количества в пул производит исключительно та операция, которая фактически совершила переход.

### 5.6. Продвижение очереди

Продвижение выполняется при каждом возврате единиц в пул: после частичного принятия, отказа, истечения срока предложения либо права, а также после подтверждения оплаты. Процедура последовательно извлекает участников из головы очереди, атомарно распределяя между ними доступное количество, пока распределение возможно.

Извлечение участника, проверка его состояния и распределение количества выполняются единственным сценарием Lua, что исключает состязание между конкурентными продвижениями. Участники, состояние которых в кэше отлично от `QUEUED`, из очереди удаляются как утратившие актуальность.

При недоступности долговременного хранилища в момент продвижения выполняется компенсация: количество возвращается в пул, а участник помещается обратно в очередь с сохранением исходного порядкового номера, вследствие чего его позиция не ухудшается.

### 5.7. Согласованность при конкурентных запросах

Изменения `available_units` и `product_count` для одного товара выполняются исключительно сценариями Lua, исполняемыми Redis атомарно и однопоточно. Это гарантирует, что при одновременном поступлении двух запросов на последнюю единицу право получит лишь один из них.

Указанное свойство составляет технический ответ на ключевой вопрос кейса: очередь FIFO определяет, **кому** достанется единица, атомарность операции над остатком — что она **не будет выдана дважды**. Подробное изложение приведено в `docs/storage/redis.md`, раздел 3, и `docs/storage/postgres.md`, раздел «Разграничение гарантий».

### 5.8. Защита от обхода очереди

Требование кейса состоит в невозможности перейти к оформлению заказа без действующего права. Проверка выполняется явным клиентским вызовом `GET /rights/{token}` к Queue Service до обращения браузера к AvitoBackend. Код `200` означает, что право действует и принадлежит обратившемуся; коды `403` и `404` означают отказ.

Выбор в пользу клиентской проверки, а не внутреннего вызова AvitoBackend → Queue Service на каждое создание заказа, обусловлен нагрузкой: поскольку проверка обязательна в любом случае, недействительные попытки дешевле отсекать на стороне Queue Service, до того как запрос достигнет конечной точки оформления заказа. AvitoBackend в основном сценарии не обязана самостоятельно проверять право, так как клиентское приложение обращается к ней исключительно после успешной проверки.

Сценарий 2 в `docs/diagrams.md` демонстрирует отклонение попытки предъявить чужое право: проверка завершается кодом `403` на стороне Queue Service, до какого-либо обращения к внешней системе.

### 5.9. Каналы реального времени

Участник открывает канал реального времени сразу после первого ответа, независимо от того, получил ли он право немедленно либо был помещён в очередь. Канал необходим и обладателю права: подтверждение `PURCHASED` поступает асинхронно, поскольку оплата проводится внешней системой (п. 8).

Реализованы два транспорта:

- **WebSocket** — `GET /queue/{product_id}/members/me` с заголовком `Upgrade: websocket`; используется клиентским приложением для отслеживания членства в конкретной очереди;
- **Server-Sent Events** — тот же ресурс с заголовком `Accept: text/event-stream`, а также `GET /me/queues` для экрана «Мои очереди».

Оба транспорта размещены на существующих ресурсах: одно состояние — один ресурс, различаются лишь представления. Добавление Server-Sent Events не нарушило работу ранее подключённых клиентов WebSocket.

Сообщения, публикуемые в Redis, представляют собой сигналы инвалидации, а не готовые представления состояния: получив сигнал, обработчик повторно читает текущее состояние и передаёт клиенту исключительно фактическое изменение. Такой порядок исключает передачу устаревших данных при конкурентных изменениях.

Обращение к `GET /queue/{product_id}/members/me` без предшествующего входа в очередь возвращает код `404`.

### 5.10. Подтверждение присутствия клиента

Соединение WebSocket применяется дополнительно как признак присутствия обладателя права. С периодичностью `RIGHT_HEARTBEAT_INTERVAL` сервер направляет управляющий кадр `Ping`; успешный ответ продлевает краткосрочную аренду права в Redis. Отсутствие подтверждения в течение `RIGHT_HEARTBEAT_TIMEOUT` приводит к освобождению права до исчерпания полного срока `RIGHT_TTL`.

Обоснование: пользователь, закрывший вкладку, с высокой вероятностью не завершит оплату, а удерживаемая им единица недоступна остальным до истечения полного срока. Продление ограничено сверху моментом `expires_at` права: подтверждение присутствия сокращает время удержания, но не продлевает право сверх выданного срока.

## 6. Состояния пользователя

Внешние состояния членства: `QUEUED`, `RIGHT_ACTIVE`, `OFFER_PENDING`, `DECLINED`, `PURCHASED`, `SOLD_OUT`. Терминальными являются три последних.

Внутренние состояния права `EXPIRED` и `USED` наружу как отдельные состояния не передаются: их последствия наблюдаются через терминальное `DECLINED` при истечении срока и `PURCHASED` при использовании.

Ответы прикладного интерфейса не содержат человекочитаемых полей `message` и `error`. Передаётся исключительно машиночитаемое состояние; сопоставление состояния с текстом выполняет клиентское приложение. Решение принято в пользу минимальности контракта и однозначного распределения ответственности.

## 7. Позиция в очереди и прогноз ожидания

Поля `position` и `eta_seconds` передаются в состоянии `QUEUED` конечными точками `GET /queue/{product_id}/members/me` и `GET /me/queues`. Ответ на `POST` их не содержит.

Позиция вычисляется по рангу участника в упорядоченном множестве Redis и приводится к отсчёту с единицы. Прогноз определяется как произведение числа предшествующих участников, уменьшенного на число свободных единиц, на среднюю длительность оплаты `AVG_PAYMENT_TIME`; при неположительном результате прогноз равен нулю.

Величина является оценочной и не составляет обязательства. Отказ от её вычисления при недоступности данных очереди не приводит к ошибке ответа: карточка без позиции сохраняет полезность, и устаревшее состояние очереди не должно нарушать работу экрана.

## 8. Подтверждение оплаты

AvitoBackend не осведомлена о внутренней модели состояний Queue Service, вследствие чего оплата подтверждается событием, а не требуемым состоянием: `POST /rights/{token}/events` с телом `{ event: "payment_succeeded", order_id }` и ответом `202 Accepted`.

Последствия:

- одной транзакцией PostgreSQL право переводится в `USED` с фиксацией `order_id` и `used_at`, а `product_count` уменьшается на количество, закреплённое за правом; условие уменьшения включает достаточность остатка, что исключает превышение фактического количества;
- соответствующее уменьшение применяется к кэшу Redis, членство переводится в терминальное состояние `PURCHASED`, таймер истечения снимается;
- выполняется вызов `PATCH /products/{product_id}/stock` к AvitoBackend, являющейся источником истины по физическому остатку;
- выполняется продвижение очереди; участники, для которых остаток исчерпан, получают состояние `SOLD_OUT`.

Обработка идемпотентна: повторное сообщение о ранее учтённой оплате возвращает `202` и не приводит к повторным внешним воздействиям.

Сбой уведомления AvitoBackend не отменяет операцию. Оплата к этому моменту уже проведена, а собственное состояние зафиксировано, вследствие чего единственно допустимой реакцией является запись в журнал с последующим устранением расхождения сверкой.

Подтверждение `PURCHASED` направляется покупателю асинхронно по каналу реального времени, а не в ответе на запрос HTTP, поскольку оформление заказа инициируется клиентским приложением непосредственно к AvitoBackend (п. 5.8), и Queue Service в синхронном пути оплаты не участвует.

## 9. Инициализация остатка

При обработке входа в очередь, не завершившегося идемпотентным возвратом существующего членства, Queue Service запрашивает у AvitoBackend текущий остаток товара: `GET /products/{product_id}/stock` с ответом `{ available: N }`.

Полученное значение применяется условно: запись в кэш Redis выполняется исключительно при отсутствии локального состояния товара, вследствие чего повторные запросы не переопределяют уже ведущийся локальный учёт. Долговременная копия сохраняется в таблице `product_stock` аналогичным образом.

Такой порядок означает, что обращение к внешней системе выполняется при каждом новом входе в очередь, а не однократно на товар. Решение принято осознанно: обращение недорого, вынесено за пределы атомарного распределения и не влияет на его результат, тогда как отслеживание факта первичной инициализации потребовало бы дополнительной синхронизации между экземплярами сервиса.

## 10. Осознанные упрощения

- **Восполнение остатка** вынесено за пределы MVP. Состояние `SOLD_OUT` является терминальным и не имеет обратного перехода: при достижении нулевого остатка товар считается исчерпанным окончательно.
- **Ограничение количества единиц на одного пользователя** не вводится: пользователь потенциально может получить столько единиц, сколько запросил, в пределах фактического остатка.
- **Политика удаления терминальных записей** из кэша не определена. Для демонстрации несущественна, подлежит определению до продолжительной эксплуатации.
- **Отдельный журнал событий очереди** в схеме не предусмотрен. Таблица `queue_memberships` хранит текущее состояние, а не последовательность переходов.

## 11. Дополнительные возможности

Кейс предусматривает дополнительные функции, усиливающие решение, — например, предложение аналогичного товара другого продавца при исчерпании остатка (`BR-4`). В настоящей редакции такие функции не спроектированы и не реализованы.

Реализованные сверх обязательного объёма возможности: публичные показатели спроса (`GET /queue/{product_id}/stats`), экран «Мои очереди» (`GET /me/queues`), прогноз времени ожидания и подтверждение присутствия клиента.

## 12. Разобранные краевые случаи

Сценарии приведены в `docs/diagrams.md`:

1. **Сценарий 1** — единственный покупатель; право выдаётся немедленно, очередь не образуется.
2. **Сценарий 2** — состязание за единственную единицу; первый покупатель бездействует до истечения срока, право переходит второму, который завершает оплату. Дополнительно демонстрируется отклонение попытки предъявить чужое право.
3. **Сценарий 3** — состязание за единственную единицу; первый покупатель завершает оплату до истечения срока, вследствие чего оба опоздавших получают состояние `SOLD_OUT`.
4. **Сценарий 4** — товар с остатком в четыре единицы; демонстрируются частичное предложение, принятие меньшего количества, немедленная выдача предложения следующему участнику при возврате единиц в пул и отказ от предложения. Товар остаётся частично нераспроданным, что является допустимым исходом.

## 13. Закрытые вопросы

- **Структура идентификатора права.** Обсуждавшийся вариант с кодированием данных внутри идентификатора отклонён. Применяется непрозрачное значение UUID (п. 4).
- **Способ проверки права внешней системой.** Проверка выполняется клиентским вызовом `GET /rights/{token}` к Queue Service (п. 5.8). Обязанность AvitoBackend самостоятельно проверять право в основном сценарии снята.
- **Авторизация межсервисного взаимодействия.** Применяется разделяемый секрет в заголовке `X-Internal-Token`, передаваемый в обоих направлениях: Queue Service предъявляет его при обращении к AvitoBackend, AvitoBackend — при уведомлении об оплате. Пустое значение отключает проверку, что допустимо исключительно при локальной разработке.
- **Выбор хранилищ.** Redis обслуживает горячий путь: очередь, атомарное распределение остатка сценариями Lua, таймеры истечения, публикация событий. PostgreSQL является долговременным источником истины по правам, членству и остатку. Обоснование приведено в `docs/storage/redis.md` и `docs/storage/postgres.md`, определения схемы — в `backend/internal/migrations/`.

## 14. Открытые вопросы

- **Ограничение источников соединений WebSocket.** В текущей редакции проверка источника при установлении соединения отключена, поскольку клиентское приложение обслуживается с иного источника. Ограничение подлежит определению совместно с параметрами промышленного развёртывания.
- **Политика удаления терминальных записей** из кэша Redis (п. 10).
- **Дополнительные возможности**, усиливающие решение по критерию `BR-4` (п. 11).
