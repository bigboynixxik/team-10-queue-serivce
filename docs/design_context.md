## Бизнес-задача (из кейса)

Товар с ограниченным остатком; несколько покупателей могут одновременно дойти до оплаты, а купить может только часть из них (асинхронная оплата). Нужен сервис очереди, который:
1. Ставит пользователя в очередь перед чекаутом.
2. Не допускает продажи одной единицы нескольким покупателям одновременно.
3. Не допускает обхода очереди (переход к покупке без активного права).
4. Даёт пользователю понятные состояния — без «серой зоны».
5. Органично встраивается в существующий сценарий покупки на Авито.

Вне скоупа (уже считается реализованным): регистрация/авторизация, полноценное оформление заказа и оплата, хранение и списание физического остатка товара — это делает внешний **AvitoBackend** (абстрактный, вне нашей реализации; инкапсулирует все условно существующие API текущего бэкенда Авито — не только чекаут, но и данные о товаре/остатке).

## Ключевая терминология

- **Queue Service (QS)** — наш backend, предмет разработки.
- **AvitoBackend (AB)** — внешний бэкенд Авито, инкапсулирующий условно существующие API: оформление заказа и оплату, а также хранение физического остатка товара. Вне скоупа, но с ним есть контракт взаимодействия (см. ниже) — в т.ч. два эндпоинта, которые Queue Service вызывает как клиент: получение остатка и его уменьшение после покупки (см. п.7).
- **`product_count`** — физический остаток товара, целое число, стартует от `total_stock`, уменьшается на `quantity` при каждой успешной покупке. Раньше называлось `sold_count` и росло по направлению к `total_stock` — переименовано и инвертировано для интуитивности («сколько осталось», а не «сколько продано»). AvitoBackend — источник истины по этому значению; то, что хранит Queue Service — это локальный кэш, инициализируемый через `GET /products/{product_id}/stock` и обновляемый после каждой оплаты через `PATCH /products/{product_id}/stock`, используемый для быстрой атомарной логики очереди (FIFO/аллокация без синхронного похода во внешний сервис на каждый чих).
- **`available_units`** — сколько единиц свободно для выдачи **прямо сейчас**, с учётом уже выданных, но ещё не оплаченных прав/предложений (они временно «замораживают» единицы на себе). `available_units <= product_count`.
- **Право на покупку (right)** — временный, персональный, непередаваемый токен, дающий возможность оформить заказ на конкретное количество товара в течение ограниченного времени (`expires_at`).
- **FIFO-очередь** — единственная политика справедливости; позиция пользователя в очереди не отображается на фронте намеренно (см. «Отклонённые фичи»).

## Модель данных (концептуально)

Право на покупку имеет поля: `token`, `user_id` (владелец), `product_id`, `quantity`, `status` (внутренний: ACTIVE / EXPIRED / USED), `expires_at`. Токен непередаваем — проверка владельца выполняется по `user_id`, привязанному к аккаунту, а не к сессии/устройству (осознанное решение: иначе можно передать право другому человеку через шаринг сессии).

## Основная бизнес-логика

### 1. Точка входа
Пользователь находится на странице товара, нажимает «Купить». Нет отдельного экрана «выбора количества» до входа в очередь — количество указывается сразу в запросе на вход (`POST /queue/{product_id}/members { quantity }`).

### 2. Решение при входе в очередь
При `POST /queue/{product_id}/members` с указанным `quantity` возможны 4 исхода (проверяется сразу, независимо от того, пуста очередь или нет — если пользователь оказывается первым в очереди, эффект тот же, что и «мгновенно»):

| Условие | Статус | Смысл |
|---|---|---|
| `available_units >= quantity` и очередь пуста | `RIGHT_ACTIVE` | Право выдано сразу на всё запрошенное количество, экран ожидания не показывается |
| `0 < available_units < quantity` | `OFFER_PENDING` | Доступно меньше, чем просили — частичное предложение с полем `available_quantity` |
| `available_units == 0`, но `product_count > 0` | `QUEUED` | Встаёт в конец FIFO-очереди, ждёт экран ожидания |
| `product_count == 0` | `SOLD_OUT` (409) | Товара больше нет вообще, освобождения не предвидится |

`OFFER_PENDING` может прийти как мгновенно при входе (если пользователь один и уже сейчас доступно меньше, чем он просит), так и позже через WS push — когда очередь дошла до него, а к этому моменту освободилось меньше единиц, чем он изначально запросил.

### 3. Реакция на `OFFER_PENDING`
Пользователь должен явно отреагировать до истечения `expires_at` предложения:
- **Принять меньшее количество**: `PATCH /queue/{product_id}/members/me { quantity }`, где `1 <= quantity <= available_quantity`. Переводит в `RIGHT_ACTIVE` с новым `quantity` и выдаёт токен. Неиспользованный остаток (`available_quantity - quantity`) немедленно возвращается в общий пул — если этого хватает следующему в очереди, тот сразу получает своё право/предложение (очередь не «зависает» из-за частичного принятия).
- **Отказаться**: `DELETE /queue/{product_id}/members/me`. Ответ `204`, затем WS push `{ status: DECLINED }` — финальное состояние для этого пользователя. Удержанное количество полностью возвращается в пул.
- **Ничего не делать до истечения таймера**: предложение снимается автоматически и переводится в терминальное `DECLINED` (эквивалентно явному `DELETE`), WS push `{ status: DECLINED }`, удержанное количество возвращается в пул. Истечение `RIGHT_ACTIVE` приводит к тому же внешнему статусу: пользователь выходит из механики и при желании должен войти в очередь заново.

`quantity` при входе в очередь ограничен сверху физическим остатком (`quantity <= product_count`) — запрос с большим значением отклоняется как `400 Bad Request` ещё до входа в очередь/выдачи предложения, это просто валидация ввода, а не бизнес-логика распределения.

### 2.1 Повторный вход в очередь (идемпотентность `POST`)
Если пользователь, уже имеющий активное членство в очереди на этот товар (`QUEUED`/`RIGHT_ACTIVE`/`OFFER_PENDING`), повторно вызывает `POST /queue/{product_id}/members` (двойной клик, ретрай сети) — запрос идемпотентен: возвращается текущее состояние членства как есть, новая запись не создаётся, `quantity` не пересчитывается. Так фронтенд может безопасно ретраить `POST` без риска завести пользователю вторую позицию в очереди на тот же товар.

### 2.2 Согласованность при конкурентных запросах
Все изменения `available_units`/`product_count` для одного `product_id` выполняются как одна атомарная операция (транзакция/лок на уровне товара в БД) — это гарантирует, что при одновременном приходе двух запросов на последнюю единицу право получит только один из них, а не оба. Это и есть техническая основа ответа на ключевой вопрос кейса «почему система не продаст один товар нескольким покупателям»: FIFO определяет *кому* достанется единица, атомарность операции над остатком — что она не достанется никому лишний раз.

### 4. Истечение права (`RIGHT_ACTIVE` → `EXPIRED`)
Если пользователь с активным правом не завершает оплату до `expires_at`:
- Право помечается `EXPIRED` (внутреннее состояние, наружу как статус не отдаётся).
- Membership переводится в терминальный `DECLINED`, очищаются `current_token` и `expires_at`, пользователю отправляется WS push `{ status: DECLINED }`.
- Освободившееся количество уходит следующему в FIFO по той же логике из п.2 (полное право / частичное предложение / ничего, если и так пусто).
- Пользователь автоматически не возвращается в очередь. Для новой попытки он должен снова вызвать вход в очередь; старый токен при этом остаётся `EXPIRED`.

### 5. Защита от обхода очереди
Ключевое требование кейса: нельзя перейти к оформлению заказа без активного права. Решение: **проверка выполняется явным клиентским вызовом `GET /rights/{token}` к Queue Service, до того как браузер вообще обратится к AvitoBackend за созданием заказа**. `200` означает, что право активно и принадлежит текущему пользователю — можно идти оформлять заказ; `403`/`404` — нельзя.

Почему так, а не внутренним вызовом AvitoBackend → Queue Service на каждое создание заказа (как рассматривалось раньше): раз проверка всё равно обязательна, дешевле отсечь невалидные попытки (истёкший токен, чужой токен, отсутствие токена) на стороне Queue Service, до того как запрос долетит до эндпоинта создания заказа AvitoBackend — это снижает нагрузку именно на самый нагруженный, критичный по чекауту эндпоинт. AvitoBackend в базовом сценарии больше не обязан сам валидировать право — фронтенд гарантированно приходит к нему только после успешной проверки в Queue Service.

Демонстрация в диаграммах (сценарий 2): второй покупатель пробует проверить чужой токен (`GET /rights/{token_A}`) — Queue Service отклоняет запрос (403) напрямую, т.к. токен принадлежит другому `user_id`, и до AvitoBackend дело не доходит вообще.

### 6. Реалтайм-канал (WebSocket)
Каждый участник, независимо от того, получил ли он право мгновенно или встал в очередь, **открывает WS-канал сразу после первого ответа** (`GET /queue/{product_id}/members/me` с `Upgrade: websocket`). Это важно даже для того, кто получил `RIGHT_ACTIVE` мгновенно — ему всё равно нужен канал позже, чтобы получить асинхронное `PURCHASED` (после оплаты, которая идёт через внешний AvitoBackend и async-webhook, см. п.7). Раньше в диаграммах этот шаг был явно показан только для тех, кто стоял в очереди — это было упущение, исправлено во всех сценариях.

Один и тот же ресурс (`GET /queue/{product_id}/members/me`) поддерживает и разовое чтение (polling fallback), и WS-upgrade — не два разных эндпоинта.

Если пользователь вызывает `GET /queue/{product_id}/members/me`, ни разу не войдя в очередь на этот товар (`POST` не выполнялся) — ответ `404 Not Found`.

### 7. Подтверждение оплаты (событийная модель)
AvitoBackend не знает и не должен знать о внутренней модели статусов Queue Service. Поэтому оплата подтверждается через событие, а не через прямое изменение статуса:

`POST /rights/{token}/events { event: "payment_succeeded", order_id }` — вызывает AvitoBackend, отвечаем `202 Accepted`. Эффект на нашей стороне:
- право → `USED` (нельзя переиспользовать);
- `product_count -= quantity` (этого права) — обновляется локальный кэш;
- **`PATCH /products/{product_id}/stock { decrement: quantity }`** — Queue Service сообщает AvitoBackend об уменьшении остатка, т.к. AvitoBackend является источником истины по физическому остатку, а не Queue Service;
- если `product_count == 0` и очередь пуста — товар помечается `SOLD_OUT` для всех новых входов в очередь.

Финальное подтверждение `PURCHASED` покупателю уходит **асинхронно через WS**, а не как прямой ответ на HTTP-запрос — потому что чекаут инициируется фронтендом напрямую к AvitoBackend (см. п.5), и Queue Service не участвует в синхронном пути оплаты.

### 7.1 Инициализация остатка от AvitoBackend
При первом обращении к товару (первый `POST /queue/{product_id}/members` на данный `product_id`, для которого у Queue Service ещё нет локального состояния) Queue Service запрашивает текущий остаток у AvitoBackend: `GET /products/{product_id}/stock` → `{ available: N }`. Это значение становится стартовым `product_count`. Дальше Queue Service ведёт `product_count`/`available_units` локально как кэш (обновляя его через `PATCH` из п.7 после каждой оплаты) — это нужно для быстрой атомарной логики очереди (FIFO/аллокация, см. п.2.2), без синхронного похода в AvitoBackend на каждое решение о выдаче права.

## Отклонённые/сознательно упрощённые фичи (и почему)

- **Позиция в очереди / ETA** — не показывается пользователю и не отдаётся через API. Причина: не нужна для MVP, только усложняет. Решение спроектировано так, чтобы добавить это позже без breaking changes (аддитивные JSON-поля, `additionalProperties` не запрещены).
- **Человекочитаемые `message`/`error` поля в ответах API** — сознательно убраны. Backend отдаёт только машиночитаемый `status`, фронтенд сам маппит статус на текст для пользователя. Принцип минимализма, явно запрошен по ходу дизайна.
- **Кнопка «выйти из очереди» на фронте** — в MVP не реализуется для обычного `QUEUED`/`RIGHT_ACTIVE` (пользователь просто не оформляет заказ, и всё). НО метод `DELETE /queue/{product_id}/members/me` уже реально используется — для явного отказа от `OFFER_PENDING` (см. п.3). Это не «мёртвый» эндпоинт.
- **Лимит на количество единиц на одного пользователя** — решили не вводить. Сколько запросил, столько потенциально может получить (в рамках реального остатка).
- **Рестокинг товара** — вне скоупа MVP. `SOLD_OUT` (как ответ на `POST`, так и WS push) — терминальное состояние без обратного пути: если `product_count` дошёл до 0, товар считается распроданным навсегда для данной сессии кейса, повторное появление стока не поддерживается.

## Состояния пользователя (статусы API)

`RIGHT_ACTIVE`, `QUEUED`, `OFFER_PENDING`, `DECLINED`, `PURCHASED`, `SOLD_OUT`. Внутренние состояния `EXPIRED`/`USED` наружу не отдаются как отдельные статусы — их эффект виден через терминальный `DECLINED` (истечение) или `PURCHASED` (использование).

## API-контракт (сводно, детали — в `docs/api.md`)

Ресурс `/queue/{product_id}/members`:
1. `POST` — войти в очередь с `quantity`, см. п.2 выше.
2. `GET /me` (+ WS upgrade) — статус/подписка на push.
3. `PATCH /me` — принять уменьшенное количество из `OFFER_PENDING`.
4. `DELETE /me` — выйти из очереди / отказаться от предложения.

Ресурс `/rights/{token}`:
5. `GET` — публичный, вызывается браузером покупателя для проверки права перед созданием заказа в AvitoBackend (см. п.5 бизнес-логики выше).
6. `POST /events` — внутренний, вызывается AvitoBackend, репортит `payment_succeeded`.

На стороне AvitoBackend (вне нашего API, условно существующие эндпоинты, которые Queue Service вызывает как клиент, см. п.7/7.1):
- `GET /products/{product_id}/stock` — текущий остаток товара.
- `PATCH /products/{product_id}/stock { decrement }` — уменьшение остатка после оплаты.

## Разобранные краевые случаи (сценарии в `docs/diagrams.md`)

1. **Сценарий 1** — единственный покупатель, право выдаётся мгновенно, очереди нет.
2. **Сценарий 2** — гонка за 1 единицу: первый получает право, но бездействует до истечения таймера → право переходит второму по FIFO, второй успевает оплатить. Также демонстрирует попытку обхода очереди чужим токеном (403).
3. **Сценарий 3** — гонка за 1 единицу: первый успевает оплатить быстрее таймера → двое опоздавших получают `SOLD_OUT`.
4. **Сценарий 4** — многоштучный товар (`total_stock=4`): один покупатель берёт 1 сразу и полностью завершает покупку (это показано явно — до входа второго покупателя в очередь, иначе непонятно, откуда у второго доступно только 3, а не 4); второй просит 5, но доступно 3 → получает `OFFER_PENDING` сразу при входе (не после ожидания) и соглашается на 2 через `PATCH`; третий просит 2, встаёт в очередь, т.к. всё удержано вторым, а когда доходит его очередь — доступна только 1 единица → снова `OFFER_PENDING`, но уже отказывается (`DELETE` → `DECLINED`). Товар в итоге остаётся частично нераспроданным (валидный исход, не баг).

Диаграммы используют `alt`/`opt`/`par` mermaid-блоки в точках реального ветвления (принятие решения пользователем, гонка «успел/не успел»), а не для перечисления всех теоретических исходов одного и того же вызова — это сделано, чтобы не раздувать диаграммы там, где ветка и так очевидна из контекста сценария.

## Известные расхождения / незавершённые темы ⚠️

Это то, что должен знать следующий агент, прежде чем считать документацию полностью согласованной:

1. **`docs/user_story.md` не обновлён** под последние изменения: нет описания сценария 4, нет упоминания `quantity`/`OFFER_PENDING`/`PATCH`/`DECLINED`, не отражена смена модели проверки права на явный `GET /rights/{token}` до создания заказа и переименование Order Service → AvitoBackend. Это осознанное решение — диаграммы часто меняются при прототипировании, синхронизировать текстовый user story на каждой итерации сочли нецелесообразным. **Перед сдачей/финализацией `user_story.md` нужно актуализировать** (переписать раздел «Ключевые решения», таблицу состояний, добавить текстовое описание сценария 4, поправить нумерацию шагов 1–3 под текущие диаграммы, обновить терминологию).
2. **Структура токена «из трёх частей»** — в самом начале обсуждения был поднят вопрос о структуре токена (`token` содержит информацию из трёх частей), но тема не была доведена до конкретного решения и осталась открытой. Нужно вернуться к ней при проектировании реализации (что именно кодируется в токене: `product_id`? `user_id`? `expires_at`? подпись?).
3. ~~Как именно Order Service проверяет токен~~ — **вопрос снят**: проверка теперь публичная и клиентская (`GET /rights/{token}` на стороне Queue Service, см. п.5 бизнес-логики), AvitoBackend в базовом сценарии больше не обязан сам валидировать право перед созданием заказа.
4. **Как AvitoBackend авторизует служебные вызовы Queue Service** (`GET /products/{product_id}/stock`, `PATCH /products/{product_id}/stock`) — открытый вопрос. Это межсервисные (service-to-service) вызовы, для которых не определён формат аутентификации/авторизации — в рамках хакатона AvitoBackend, скорее всего, придётся частично мокать, и формат этого вызова нужно будет решить отдельно.
5. ~~Хранение данных / выбор БД~~ — **вопрос снят**: решение — Redis (hot-path: очередь, атомарный decrement через Lua, TTL-таймеры, pub/sub для WS) + Postgres (durable-источник истины по правам/членству/остатку), см. `docs/storage/redis.md` и `docs/storage/postgres.md`, DDL — в `migrations/`.
6. **Доп. функции для усиления решения** (бонус по кейсу, например «предложить аналогичный лот у другого продавца при SOLD_OUT») — не обсуждались и не спроектированы.
