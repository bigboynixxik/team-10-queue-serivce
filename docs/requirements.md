# Пользовательские истории и требования

Настоящий документ фиксирует требования к решению. Обоснование проектных решений приведено в `docs/design_context.md`, форма прикладного интерфейса — в `docs/api.yml`. Раздел 6 сопоставляет требования с их реализацией.

## 1. Пользовательские истории

**История 1. Вход в очередь и ожидание**

> **КАК** покупатель, намеренный приобрести товар ограниченной доступности,
> **Я ХОЧУ** при нажатии кнопки покупки попадать в прозрачную очередь ожидания и наблюдать своё состояние,
> **ЧТОБЫ** понимать свои шансы на покупку и не ожидать в неведении.

**История 2. Получение права на покупку**

> **КАК** покупатель, чья очередь подошла,
> **Я ХОЧУ** получить исключительное право на оформление заказа с явным ограничением по времени,
> **ЧТОБЫ** завершить оплату без риска, что товар будет приобретён другим пользователем.

**История 3. Исчерпание товара**

> **КАК** покупатель, находящийся в очереди,
> **Я ХОЧУ** получить незамедлительное и однозначное уведомление, если товар закончился до наступления моей очереди,
> **ЧТОБЫ** не продолжать бессмысленное ожидание и иметь возможность перейти к другим предложениям платформы.

## 2. Бизнес-требования (BR)

- **BR-1.** Система должна исключать возможность приобретения одной единицы товара несколькими покупателями.
- **BR-2.** Внедрение сервиса должно предотвращать превышение числом оформленных заказов фактического остатка товара.
- **BR-3.** Сервис должен встраиваться в существующий путь пользователя на платформе.
- **BR-4.** При исчерпании товара система должна снижать негативное впечатление и удерживать пользователя на платформе, например предлагая аналогичные товары других продавцов.

## 3. Пользовательские требования (UR)

- **UR-1.** Пользователь должен наблюдать прозрачное состояние ожидания в очереди.
- **UR-2.** Пользователь должен однозначно понимать свой следующий шаг в каждом состоянии интерфейса.
- **UR-3.** Пользователь должен получать исключительное право на оформление заказа с ограничением по времени.
- **UR-4.** Пользователь должен получать незамедлительное уведомление об исчерпании товара до наступления его очереди.

## 4. Функциональные требования (FR)

### 4.1. FR-A. Управление очередью и состояниями

- **FR-A1.** При попытке приобрести товар ограниченной доступности система должна помещать пользователя в очередь.
- **FR-A2.** Система должна отображать экран ожидания с однозначными состояниями и сообщениями.
- **FR-A3.** Система должна проверять доступность товара перед выдачей права на покупку.

### 4.2. FR-B. Механика права на покупку

- **FR-B1.** Система должна выдавать временное право на покупку при наступлении очереди.
- **FR-B2.** Право на покупку должно быть закреплено за конкретным пользователем.
- **FR-B3.** Система должна исключать повторное использование выданного права.
- **FR-B4.** Система должна исключать передачу права другому пользователю.

### 4.3. FR-C. Защита от обхода очереди

- **FR-C1.** Система должна проверять наличие действующего права на покупку именно этого товара перед допуском к оформлению заказа.
- **FR-C2.** Система должна отклонять попытки миновать очередь.

### 4.4. FR-D. Ограничения MVP

- **FR-D1.** Полноценная регистрация и авторизация пользователя не реализуется. Идентификатор пользователя передаётся заголовком `X-User-Id`; в промышленной эксплуатации он извлекался бы из сессии.
- **FR-D2.** Реальное проведение оплаты не реализуется. Оплата имитируется страницей заглушки внешней системы.
- **FR-D3.** Списание физического остатка товара находится вне области решения: источником истины по остатку является внешняя система AvitoBackend. Queue Service ведёт локальное зеркало остатка, необходимое для атомарного распределения, и уведомляет внешнюю систему об уменьшении после каждой подтверждённой оплаты — через транзакционный почтовый ящик с гарантией доставки.
- **FR-D4.** Решение сосредоточено на основном пользовательском сценарии.
- **FR-D5.** Восполнение остатка товара не поддерживается: состояние `SOLD_OUT` является терминальным.

## 5. Нефункциональные требования (NFR)

- **NFR-1. Стек серверной части.** Серверная часть реализуется на языке Go.
- **NFR-2. Стек клиентской части.** Клиентская часть реализуется на React версии не ниже 18 с применением TypeScript.
- **NFR-3. Развёртывание.** Приложение разворачивается средствами Docker Compose.
- **NFR-4. Защищённость права.** Временное право на покупку должно быть технически защищено от подделки и присвоения.
- **NFR-5. Контроль качества.** На серверной и клиентской частях настраиваются статические анализаторы с обоснованием правил; конфигурация серверной части размещается в `backend/.golangci.yaml`.

## 6. Соответствие требований реализации

| Требование | Реализация |
| --- | --- |
| BR-1, BR-2, FR-A3 | Атомарное распределение остатка сценариями Lua в Redis; исключительная блокировка членства для параллельных запросов одного пользователя; транзакция подтверждения оплаты с условием достаточности остатка (`docs/storage/postgres.md`, раздел 5) |
| BR-3 | Вход в очередь по нажатию кнопки покупки на странице товара; оформление заказа остаётся за внешней системой |
| BR-4 | **Не реализовано.** Дополнительные возможности не спроектированы (`docs/design_context.md`, п. 11) |
| UR-1, FR-A2 | Состояния членства, позиция в очереди и прогноз ожидания; публичные показатели спроса `GET /queue/{product_id}/stats` |
| UR-2 | Ответ содержит исключительно машиночитаемое состояние; сопоставление состояния с текстом и следующим шагом выполняет клиентское приложение |
| UR-3, FR-B1, FR-A1 | Конечный автомат очереди: `QUEUED`, `RIGHT_ACTIVE`, `OFFER_PENDING`; срок действия права `RIGHT_TTL` |
| UR-4 | Терминальное состояние `SOLD_OUT`, передаваемое по каналу реального времени при продвижении очереди с нулевым остатком |
| FR-B2, FR-B4, NFR-4 | Непрозрачный идентификатор права UUID; принадлежность проверяется сравнением `user_id` (`docs/design_context.md`, п. 4) |
| FR-B3 | Перевод права в `USED` в транзакции с условием текущего состояния `ACTIVE` |
| FR-C1, FR-C2 | Два рубежа: клиентский `GET /rights/{token}` — чужое право отклоняется кодом `403`, недействительное кодом `404`; служебный `POST /internal/rights/{token}/validate`, вызываемый AvitoBackend перед созданием заказа, — граница доверия, проверяющая привязку права к товару |
| NFR-1 | Go 1.26, стандартная библиотека `net/http` и `log/slog` |
| NFR-2 | React 19 и TypeScript 5; требование «не ниже 18» удовлетворено |
| NFR-3 | `docker-compose.yml`: пять служб, миграции применяются при инициализации |
| NFR-5 | `backend/.golangci.yaml` и `frontend/biome.json` |

## 7. Реализовано сверх обязательного объёма

Перечисленные возможности не следуют из требований кейса и добавлены как усиление основного сценария; ни одна из них не подменяет обязательную механику.

- **Публичные показатели спроса** — `GET /queue/{product_id}/stats`. Продавцу показывают, оправдано ли восполнение остатка; покупателю — что ожидание обусловлено реальным спросом (`UR-1`).
- **Экран «Мои очереди»** — `GET /me/queues` с потоком Server-Sent Events. Позволяет наблюдать участие сразу в нескольких очередях.
- **Позиция и прогноз ожидания** — поля `position` и `eta_seconds` в состоянии `QUEUED`.
- **Подтверждение присутствия клиента** — освобождение права до исчерпания полного срока, если обладатель закрыл вкладку (`docs/design_context.md`, п. 5.10).
- **Частичное предложение** — состояние `OFFER_PENDING` и принятие меньшего количества. Позволяет не отклонять запрос целиком, когда доступного количества недостаточно.
- **Восстановление состояния при запуске** — содержимое Redis воссоздаётся из PostgreSQL до начала приёма запросов, включая исправление записей, противоречащих конечному автомату (`docs/design_context.md`, пп. 9.1–9.2).
- **Гарантированная доставка уведомлений внешней системе** — уменьшение остатка фиксируется в таблице `stock_decrement_outbox` той же транзакцией, что и оплата, и доставляется фоновым обработчиком с повторными попытками (`docs/design_context.md`, п. 8.2).
