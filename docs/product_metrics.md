# Аналитика спроса для продавца (Метрики Queue Service)

Настоящий документ описывает состав, архитектуру сбора и ограничения аналитических показателей, предоставляемых продавцам платформы. Данные метрики предназначены для оценки спроса на товары ограниченной доступности, выявления упущенной выгоды и анализа поведения покупателей.

Конечная точка `GET /api/v1/seller/products/{product_id}/metrics` выделена в отдельный ресурс. Это изолирует тяжелые аналитические запросы от публичного интерфейса состояния очереди (`/stats`).

## 1. Состав метрик

Показатели разделены на логические группы. Значения `product_id` и базовая `price` товара принадлежат внешней системе (AvitoBackend) и не хранятся в Queue Service.

### 1.1. Спрос и дефицит

- **Коэффициент дефицита:** Отражает уровень ажиотажа. Состоит из двух абсолютных величин:

    - `total_stock`: Исходное количество товара, заявленное к продаже. Извлекается из таблицы `product_stock`.

    - `total_contenders`: Общее число уникальных пользователей, попытавшихся приобрести товар (нажавших кнопку покупки). Извлекается из таблицы `queue_memberships`.

    - _Обоснование:_ Клиентское приложение самостоятельно вычисляет соотношение (например, «на 10 штук претендуют 200 человек»).
        

### 1.2. Конверсия выданных прав

- **Успешные покупки:** Количество прав на покупку, по которым была успешно завершена оплата. Извлекается по статусу `USED` в таблице `rights`.
    
- **Неоплаченные права:** Количество прав, выданных пользователям, но не оплаченных до истечения срока (`RIGHT_TTL`). Извлекается по статусу `EXPIRED` в таблице `rights`.
    
    - _Обоснование:_ Демонстрирует долю немотивированной аудитории, которые заняли товар, но отказались от покупки на этапе чекаута.
        

### 1.3. Отказы и упущенная выгода

- **Отказ по исчерпанию (Soldout):** Количество пользователей, до которых дошла очередь, но физический остаток товара оказался равен нулю. Извлекается по статусу `SOLD_OUT` в таблице `queue_memberships`.
    
    - _Метрика потерянных денег:_ Queue Service отдает исключительно абсолютное число отказов. Клиентское приложение умножает это значение на `price` товара для отображения потенциальной выручки, которую продавец мог бы получить при наличии достаточного остатка.
        
- **Добровольные отказы:** Количество пользователей, покинувших очередь до получения права на покупку.
    
    - _Вычисление:_ Подсчитываются строки `queue_memberships` со статусом `DECLINED`, для которых отсутствует связанная запись в таблице `rights` (по `user_id` и `product_id`). Это позволяет отфильтровать тех, кто ушел сам на этапе ожидания, от тех, чье выданное право просто истекло по таймеру.
        

### 1.4. Временные показатели

- **Время до оплаты:** Среднее время, затраченное пользователями на ввод платежных данных.
    
    - _Вычисление:_ Разница `used_at - created_at` для записей в статусе `USED` в таблице `rights`. Используется для корректировки конфигурации `AVG_PAYMENT_TIME`.
        
- **Время ожидания до отказа:** Среднее время, проведенное в очереди пользователями, которые покинули ее до получения права на покупку.
    
    - _Вычисление:_ Разница `updated_at - created_at` в таблице `queue_memberships` для группы «Добровольные отказы». Возвращается в целых секундах. Сигнализирует о пределе терпимости аудитории к ожиданию.
## 2. Архитектура сбора данных

Сбор метрик выполняется **исключительно из PostgreSQL**. Redis обслуживает горячий путь и аналитическими запросами не нагружается. PostgreSQL выступает как долговременный источник истины, хранящий полный слепок состояний.

Для минимизации сетевых издержек (I/O) и нагрузки на пул соединений `pgx`, сбор показателей выполняется через Conditional Aggregation. Вместо семи раздельных запросов `SELECT COUNT(...)`, сервис выполняет по одному запросу к каждой таблице с использованием оператора `FILTER (WHERE ...)`:

```SQL
-- Запрос к таблице queue_memberships (Метрики отказов и ожидания)
SELECT 
    COUNT(id) AS total_contenders,
    COUNT(id) FILTER (WHERE status = 'SOLD_OUT') AS soldout_count,
    AVG(EXTRACT(EPOCH FROM (updated_at - created_at))) FILTER (WHERE status = 'DECLINED' AND r.token IS NULL) AS avg_dropoff_time,
    COUNT(id) FILTER (WHERE status = 'DECLINED' AND r.token IS NULL) AS dropoff_count
FROM queue_memberships qm
LEFT JOIN rights r ON qm.user_id = r.user_id AND qm.product_id = r.product_id
WHERE qm.product_id = $1;

-- Запрос к таблице rights (Метрики конверсии и времени оплаты)
SELECT 
    COUNT(token) FILTER (WHERE status = 'USED') AS used_rights_count,
    COUNT(token) FILTER (WHERE status = 'EXPIRED') AS expired_rights_count,
    AVG(EXTRACT(EPOCH FROM (used_at - created_at))) FILTER (WHERE status = 'USED') AS avg_payment_time
FROM rights
WHERE product_id = $1;

-- Запрос к таблице product_stock (Исходный остаток)
SELECT total_stock 
FROM product_stock 
WHERE product_id = $1;
```

## 3. Индексирование и баланс производительности (Read/Write Trade-off)

Для обеспечения приемлемого времени отклика при агрегации десятков тысяч строк в схему БД добавляется композитный индекс:

```SQL
CREATE INDEX idx_queue_memberships_product_status ON queue_memberships (product_id, status);
```

**Обоснование компромисса:**

Индексы создают накладные расходы при операциях записи (`INSERT` и `UPDATE`). Однако профиль нагрузки очереди асимметричен:

1. Пиковая запись происходит кратковременно (момент старта продаж лимитированного товара).
    
2. После распродажи или перехода пользователей в терминальные состояния таблица переходит в режим интенсивного аналитического чтения (продавец регулярно обновляет дашборд).

В отсутствие данного индекса PostgreSQL был бы вынужден выполнять `Heap Fetch` для фильтрации статусов. Композитный индекс позволяет планировщику применять `Index Only Scan`, выполняя подсчет `COUNT` непосредственно в дереве индекса, находящемся в оперативной памяти. Накладные расходы на запись окупаются предотвращением деградации производительности БД при построении отчетов.

## 4. Ограничения MVP и пути масштабирования

В рамках текущего MVP метрики рассчитываются синхронно в базе данных при каждом вызове конечной точки.

### Направление масштабирования

При переходе к промышленным нагрузкам платформы Авито синхронный расчет по транзакционной БД становится узким местом. Целевое состояние системы требует внедрения согласованности в конечном счете (Eventual Consistency):

1. **Асинхронный воркер:** Логика SQL-агрегации выносится в фоновый процесс (горутину `runMetricsBuilderWorker`), аналогичный механизмам обработки истечений (`ProcessExpirations`) и доставки списаний (`ProcessStockDecrementOutbox`).
    
2. **Кэширование аналитики:** Воркер с заданной периодичностью формирует JSON-отчет по активным товарам и сохраняет его в Redis.
    
3. **Изоляция:** Конечная точка `GET /api/v1/seller/products/{product_id}/metrics` перестает обращаться к PostgreSQL, возвращая закэшированный ответ из Redis за $O(1)$. Задержка обновления дашборда на 1-2 минуты является общепринятым стандартом для аналитических интерфейсов.
