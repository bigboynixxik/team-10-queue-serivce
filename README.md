# Авито Очередь (MVP)

Сервис пользовательской очереди на покупку дефицитного товара. Кейс 2 хакатона Авито, команда 10.

Репозиторий содержит серверную часть на Go, клиентскую часть на React, заглушку внешней системы Авито, браузерное расширение и проектную документацию. Приложение целиком разворачивается одной командой через Docker Compose.

**Развёрнутое приложение доступно по адресу http://81.26.179.126/avito** — основной сценарий воспроизводится без локального запуска.

## 1. Контекст проблемы
На платформе регулярно появляются лимитированные или дефицитные товары (редкие позиции, распродажи), спрос на которые многократно превышает доступное количество. Из-за асинхронной работы процесса оплаты возникает проблема: несколько пользователей могут одновременно начать оформлять заказ на один и тот же товар.
В результате количество оформленных заказов превышает фактический остаток на складе. Пользователь тратит время на оформление, но в конце узнает, что товар недоступен. Это вызывает негатив, снижает лояльность к платформе и создает повышенную нагрузку на системы.

## 2. Бизнес-цель
Создать MVP сервиса пользовательской очереди, который:
1. Ставит покупателя в очередь перед переходом к оплате.
2. Защищает систему от некорректного распределения товаров (исключает возможность одновременной покупки одной единицы товара несколькими людьми).
3. Выдает временное и защищенное право на покупку.
4. Органично вписывается в существующий путь пользователя на платформе.

## 4. Развёртывание и запуск

### 4.1. Развёрнутое приложение

Приложение развёрнуто на сервере и доступно по адресу http://81.26.179.126/avito. Проверка основного сценария не требует локального запуска; порядок проверки изложен в п. 4.4.

Подготовка сервера автоматизирована средствами Ansible. Каталог [`infra/ansible/`](infra/ansible/) содержит playbook, устанавливающий Docker и сопутствующие пакеты; параметры подключения (`HOST_IP`, `SSH_USER`, `SSH_PRIVATE_KEY`) задаются файлом окружения и в репозитории не хранятся.

### 4.2. Локальный запуск

Требуется Docker с плагином Compose. Из корневого каталога репозитория:

```bash
cp backend/.env.example backend/.env
docker compose up -d --build
docker compose ps
```

Готовность подтверждается переходом всех пяти служб в состояние `healthy`. Миграции схемы применяются автоматически.

Адреса служб при локальном запуске:

| Служба | Адрес | Назначение |
| --- | --- | --- |
| `frontend` | http://localhost/avito | Клиентское приложение, проксирование `/api` |
| `backend` | http://localhost:8080 | Прикладной интерфейс, WebSocket, SSE |
| `avitomock` | http://localhost:9090 | Заглушка внешней системы: остаток товара и страница оформления заказа |
| `postgres` | `localhost:5432` | Долговременное хранилище |
| `redis` | `localhost:6379` | Очередь, распределение остатка, публикация событий |

Предусмотрен также `Taskfile.yml`: команда `task up` выполняет создание файлов окружения, сборку и запуск, `task down` — остановку.

### 4.3. Режим разработки

Порядок запуска отдельных частей вне контейнеров описан в [`backend/README.md`](backend/README.md), раздел 3.2, и [`frontend/README.md`](frontend/README.md), раздел «Как запустить».

### 4.4. Проверка основного сценария

Ключевое свойство решения проявляется при состязании двух покупателей, поэтому остаток товара следует привести к единице. При локальном запуске:

```bash
curl -X PUT http://localhost:9090/products/demo-1/stock \
-H 'Content-Type: application/json' -d '{"available":1}'
```

Далее откройте приложение в двух разных браузерных профилях либо в обычном и приватном окне, чтобы выступать двумя пользователями, и нажмите кнопку покупки в обоих. Право на покупку получит один, второй будет помещён в очередь. При завершении оплаты первым второй незамедлительно получает состояние `SOLD_OUT`; при бездействии первого право переходит второму по истечении срока `RIGHT_TTL`.

## 7. Особенности реализации

### 7.1. Право на покупку

Центральная механика решения. Право является временным, персональным и непередаваемым: оно выдаётся конкретному пользователю на конкретный товар и действует до наступления `expires_at`. Идентификатор представляет собой непрозрачное значение UUID, не содержащее кодированных данных, поэтому подделать его невозможно, а криптографическая подпись не требуется. Принадлежность устанавливается сравнением идентификатора пользователя, повторное использование исключается переводом права в состояние `USED` в транзакции.

### 7.2. Исключение двойной продажи

Решение о выдаче единицы товара принимается сценарием Lua в Redis, который исполняется атомарно и однопоточно. Два запроса на последнюю единицу физически не могут завершиться выдачей двух прав. Очередь FIFO определяет, кому достанется единица товара, а атомарность гарантирует, что она не будет выдана дважды. Ни одна из гарантий не зависит от поведения клиентского приложения.

### 7.3. Частичное предложение

Когда доступно меньше запрошенного, покупатель не получает отказ. Ему сообщается фактически доступное количество и предоставляется ограниченное время на решение. Приняв меньшее количество, он немедленно получает право на покупку, а невостребованные единицы возвращаются в пул, после чего очередь продвигается дальше и следующий участник может получить право без дополнительного ожидания. Отказ либо отсутствие ответа освобождают удерживаемое количество полностью.

Механика повышает долю успешных покупок при неизменном остатке: излишек запроса не простаивает в резерве, а одна партия товара распределяется между большим числом покупателей.

### 7.4. Защита от обхода очереди

Проверка права выполняется на двух уровнях, поскольку браузер находится под управлением пользователя и его поведение не может служить гарантией.

Клиентское приложение подтверждает право вызовом `GET /api/v1/rights/{token}` до перехода к оформлению заказа. Право, принадлежащее другому пользователю, отклоняется кодом `403`, истёкшее либо уже использованное — кодом `404`. Эта проверка отвечает за понятное поведение интерфейса и отсекает заведомо недействительные попытки прежде, чем они достигнут внешней системы.

Границей доверия служит вторая проверка, выполняемая между службами: получив запрос на оформление заказа, AvitoBackend обращается к Queue Service и создаёт заказ только после подтверждения, что предъявленное право действует и выдано именно на этот товар. Запрос защищён разделяемым секретом и клиенту недоступен. Вследствие этого попытка обратиться к оформлению напрямую, минуя очередь, отклоняется независимо от того, что делает браузер.

### 7.5. Возврат неиспользованных прав в оборот

Неоплаченное право не блокирует товар бесконечно. По истечении срока оно освобождается фоновым обработчиком, а удерживаемая единица возвращается в пул и достаётся следующему участнику очереди. Дополнительно контролируется присутствие покупателя: если клиент перестаёт подтверждать активность, право освобождается досрочно, не дожидаясь исчерпания полного срока.

### 7.6. Ограничение числа одновременных очередей

Покупатель одновременно участвует не более чем в пяти очередях; значение настраивается параметром `MAX_ACTIVE_QUEUES`. Место занимают лишь действующие участия: завершённые покупкой, отказом либо исчерпанием товара освобождают его сразу.

Ограничивается участие, но не очерёдность: место в очереди невозможно ни купить, ни ускорить, порядок FIFO механикой не затрагивается. Смысл ограничения в том, что участник не может удерживать за собой произвольное число единиц товара, недоступных прочим покупателям, пока принимает решение.

Проверка предела и занятие места выполняются одной атомарной операцией, вследствие чего одновременная отправка нескольких запросов ограничение не обходит.

### 7.7. Однозначные состояния

Пользователь всегда находится в одном из шести состояний: `QUEUED`, `RIGHT_ACTIVE`, `OFFER_PENDING`, `PURCHASED`, `DECLINED`, `SOLD_OUT`. Каждое предполагает понятный следующий шаг, промежуточных и неопределённых состояний не предусмотрено. Изменения доставляются по WebSocket и Server-Sent Events, поэтому опрос сервера клиентским приложением не требуется.

### 7.8. Встраивание в существующий продукт

Сервис не заменяет ни каталог, ни оформление заказа, ни оплату, а добавляет один шаг между кнопкой покупки и переходом к оплате. Взаимодействие с внешней системой ограничено двумя вызовами: получением остатка и уведомлением о его списании. Такая схема позволяет включать очередь выборочно, только для позиций ограниченной доступности.

Каталог «extension» содержит браузерное расширение, добавляющее кнопку перехода в очередь непосредственно на страницу объявления Авито. Расширение демонстрирует предполагаемое место сервиса в существующем пользовательском пути.

### 7.9. Устойчивость к сбоям

Сервис рассчитан на то, что внешняя система, хранилища и он сам могут оказаться временно недоступны, и ни один из этих случаев не должен приводить к расхождению между проданным и списанным.

Уведомление внешней системы о списании остатка фиксируется в той же транзакции PostgreSQL, что и сама покупка, а доставляется отдельным фоновым обработчиком с повторными попытками и нарастающей задержкой. Недоступность AvitoBackend в момент оплаты откладывает уведомление, но не теряет его и не отменяет покупку. Повторная доставка безопасна: событие снабжено уникальным идентификатором, по которому внешняя система распознаёт уже применённое списание.

Отложенные во времени переходы, то есть истечение права и снятие нерассмотренного предложения, берутся обработчиком в аренду, а не изымаются из расписания. Прекращение работы процесса в середине обработки приводит к возврату задачи в расписание по истечении аренды, вследствие чего удерживаемые единицы не остаются заблокированными.

Состояние кэша восстанавливается из PostgreSQL при запуске: остаток, порядок очереди, членства, права и таймеры воссоздаются до того, как сервис начинает принимать запросы. Полная потеря Redis приводит к паузе на время восстановления, но не к потере очереди. Записи, противоречащие конечному автомату, приводятся к согласованному состоянию с фиксацией в журнале.

Технические особенности реализации, включая версионирование прикладного интерфейса, разграничение доступа и обработку ошибок, изложены в [`backend/README.md`](backend/README.md), раздел 7.

## 9. Процесс разработки

Работа велась в общем репозитории с разделением на ветки по задачам. Ветка `main` содержит стабильное состояние, ветка `develop` — интеграционное; задачи выполняются в ветках вида `feat/*`, `fix/*`, `chore/*` и вливаются в `develop` через pull request с обязательным ревью.

Сообщения коммитов оформляются по соглашению Conventional Commits: префикс типа изменения (`feat`, `fix`, `refactor`, `chore`, `docs`), при необходимости область изменения в скобках, далее краткое описание в повелительном наклонении.

История насчитывает свыше 180 коммитов и доступна командой `git log` либо на странице репозитория. Перечень выполненных задач с обсуждением решений сохранён в списке pull request.

## 11. Ограничения MVP

Перечисленные ограничения являются следствием осознанных решений и границ кейса.

- Регистрация и авторизация не реализуются: идентификатор пользователя передаётся клиентским приложением.
- Реальное проведение оплаты не реализуется: оплата имитируется страницей заглушки внешней системы.
- Физический остаток товара принадлежит внешней системе; сервис ведёт локальное зеркало, необходимое для атомарного распределения.
- Восполнение остатка не поддерживается: состояние `SOLD_OUT` является терминальным.

Полный перечень ограничений серверной части приведён в [`backend/README.md`](backend/README.md), раздел 10.

### 11.1. Направления развития

Реализованная модель допускает расширение без пересмотра основной механики:

- подбор аналогичных товаров других продавцов при исчерпании остатка, удерживающий покупателя на платформе;
- восполнение остатка с обратным переходом из состояния `SOLD_OUT`;
- расширенная аналитика спроса для продавца на основе накопленных показателей очереди.
